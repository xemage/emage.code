# Prerequisites — emage.code implementation

## Required
- **Node.js 18+** — for `scripts/sync.mjs` and for MCP servers launched via `npx`.
- **Python 3.10+** — for `check.py`, `package.py`, and registry generation.
- **Git 2.30+** — for worktree isolation, branch policies, and pack install from git URLs. The optional `poc-security-audit` server needs **Git 2.40+** (see below).

## Browser for the `playwright` server
The `playwright` MCP server (`@playwright/mcp`) does not bundle a browser and does not download one on first use. Without it the first browser tool call fails (`Chromium distribution ... is not found`). Install the browser once, with the command pinned to the same version as the server entry:
```bash
npx -y @playwright/mcp@0.0.83 install-browser chrome-for-testing
```
- **Size:** about 670 MB on disk (Chrome for Testing, its headless shell and ffmpeg). The download comes from `cdn.playwright.dev`. The plain `playwright install chromium --no-shell` route fetches only Chromium plus ffmpeg (about 400 MB), but it needs the separate `playwright` CLI, which `npx` resolves to whatever release is current unless you pin it; it is not the lead command because it can fetch a different browser revision than the one the pinned server expects.
- **Version:** the browser revision follows the pinned `@playwright/mcp` version (`chromium-1247`, Chrome for Testing 155.0.8059.12, for 0.0.83). Each pin bump can force a new download. The browser is patched only when the pin is bumped, not by your operating system (a system Chrome would be); check the browser's security version at every pin bump.
- **What is verified about the download:** the revision, the sizes and the install time above were observed once, on one Linux host (T654). That run did not check whether Playwright verifies a checksum or signature of the downloaded archive, and this repository pins no hash of it **(unverified)**. Treat the download as trusted only to the extent that you trust `cdn.playwright.dev` and the npm package.
- **Why `--browser chromium`:** the default channel is Google Chrome, which needs an OS package and usually root. The entry sets `--browser chromium` so the Playwright-managed Chrome for Testing is used.
- **Sandbox:** the entry sets `--sandbox` (the default would run Chromium with `--no-sandbox`). `--sandbox` worked on the test host; it can fail in containers and on hosts that block unprivileged user namespaces **(unverified there)**. Removing it from your local config weakens the browser isolation; do so only knowingly, and `install.sh --update` restores the generated arguments.
- **Output directory:** browser output (page snapshots, downloads from visited pages) goes to `.playwright-mcp/` under the launch directory. It is git-ignored in this repository only; `install.sh` does not edit your project's `.gitignore`. In a project that installed emage.code, add `.playwright-mcp/` to its `.gitignore` (or point `--output-dir` at an ignored path in a user-owned entry), otherwise page content can be committed by accident.
- **What the installer prints (T672, QA-T648-02):** after every run that ends normally (a full install, `--update` and `--projections-only`), when a selected platform's generated config names the `playwright` server (the installer tests that per platform), `install.sh` prints this note on standard output, once:
  ```text
  Note: this install includes the Playwright MCP server. It does not bundle or download a
  browser, so its first browser tool call fails until you install one (once, about 670 MB):
    npx -y @playwright/mcp@0.0.83 install-browser chrome-for-testing
  Its output (page snapshots, downloads) goes to .playwright-mcp/ under the directory your
  assistant starts from, and this installer does not edit your .gitignore: add
    .playwright-mcp/
  to your project's .gitignore, otherwise page content can be committed by accident.
  (Details: implementation/PREREQUISITES.md, section "Browser for the `playwright` server".)
  ```
  The version in the command is read from the generated config, so it follows the pin; the command above is the one at the top of this section, and the size matches the **Size** bullet. The installer neither downloads the browser nor edits the `.gitignore`: both steps stay yours.

### Local apps are blocked by the shipped entry
The shipped `playwright` entry carries a `--blocked-origins` list that denies `localhost`, `127.*`, `*.localhost`, `10.*`, `192.168.*` and `172.16` to `172.31` (plus other loopback, link-local and carrier-grade-NAT forms). Its first request to a local dev server therefore fails with `net::ERR_BLOCKED_BY_CLIENT`. **The shipped entry cannot test a local app.** This is the intended hardening, not a fault.

If you need to test a local app, add a second entry of your own, named `playwright-local`, in your MCP config file (for example `.mcp.json` for Claude Code). Do not edit the arguments of `playwright` itself: they are generator-owned and `install.sh --update` restores them.
```json
"playwright-local": {
  "command": "npx",
  "args": ["-y", "@playwright/mcp@0.0.83", "--headless", "--isolated", "--browser", "chromium", "--sandbox", "--block-service-workers", "--no-webmcp"]
}
```
- **Warning:** this entry has no origin restriction. A page it opens can redirect to, or load, any address your host reaches, including internal services and cloud metadata endpoints, and the page content is returned to the model. Use it only on a development machine, only for your own pages, and remove it when you are done.
- **Survives `install.sh --update`:** `scripts/merge-mcp-json.py` keeps keys that exist only in your file, and it prunes a name only if the old provenance sidecar lists it as generator-owned or you name it in `--force-prune-keys`. `playwright-local` is neither, so it is kept (verified by reading the script and by a test in `tests/functional/test_mcp_package_pins.py`).
- **Tool names and agents:** this server's tools are named after the server (for Claude Code `mcp__playwright-local__browser_navigate`). The generated agent tool lines list tools of the `playwright` server (for example `mcp__playwright__browser_navigate`, rendered per platform), not of `playwright-local`, so on Claude Code, GitHub Copilot/VS Code and Pi (for an agent that lists an `mcp__` tool) a subagent such as `qa-engineer` does not receive the new server's tools. On Opencode and Gemini CLI an agent's tool list does not restrict MCP tools, so any agent can call them, including `browser_run_code_unsafe`; the server-level denial below covers the `playwright` server only, so `playwright-local` is not denied there. Use it from your own session on a development machine, remove it when you are done, or add the names to a local copy of an agent file (a later `--update` overwrites that copy). The per-platform tool-name forms are recorded in `docs/artifacts/mcp-tool-name-mapping-v1.md` (recorded before Cursor was removed; its Cursor rows are historical).
- **Server-level denial of six tools (T658):** on Opencode and Gemini CLI, where an agent's tool list does not restrict MCP tools, the generated configs deny `browser_run_code_unsafe`, `browser_evaluate`, `browser_file_upload`, `browser_drag`, `browser_drop` and `browser_network_request` for the shipped `playwright` server (Opencode: top-level `permission` entries `playwright_<tool>: deny` in `.opencode/opencode.json`; Gemini CLI: `excludeTools` on the `playwright` entry of `.gemini/settings.json`). The list is `denyTools` in `implementation/knowledge/mcp/servers.yaml`. This follows the vendor documentation and source and has **not been observed in a live run**. On Opencode the denial is last only inside the one file the installer writes (`install.sh --update` puts the six generated keys at the end of the top-level `permission`): Opencode merges several configuration sources, so an allow for one of these names in an agent file of your own, in another configuration source, in `OPENCODE_CONFIG_CONTENT` or in managed settings that Opencode applies later can override it. Since T663 the Opencode generator also writes per-agent `false` entries into every agent file (per-agent): the six Playwright names for every agent, and `<server>_*: false` for every server that the agent holds no token of and that is not exempt (`denyUnlessGranted: true` on gitlab, playwright, memory, sequential-thinking, security-audit, poc-security-audit, context-retriever, filesystem, git and supabase), after its allows; an agent that holds only named tools of a server (all seven GitLab holders for `gitlab`: qa-engineer, scrum-master, orchestrator, poc-orchestrator, devops-engineer, release-manager and poc-devops-engineer; the Playwright agents, the security agents, context-retriever) gets that server's wildcard first, so it can call only its named tools. The read/search and memory-layer servers brave, context7, hindsight, cwso, hf-mcp-server and toolradar are exempt (`denyUnlessGranted: false`, user decision of 2026-10-16), so generated agents, including a primary orchestrator, keep them; a non-exempt server that no agent lists (filesystem, git, supabase) is denied in every generated agent file, as on Claude Code, where a subagent without the token cannot call it; the entries are documented and read from vendor source, not observed in a live tool call (`docs/artifacts/mcp-agent-denials-v1.md`, `docs/artifacts/mcp-agent-denials-evidence-v1.md`). On Opencode the `true` entries an agent holds come after your global config, so your own global `ask` or `deny` on a tool an agent holds is silently overridden for that agent; for example a global `ask` on `gitlab_create_merge_request` is overridden for the three agents that hold it (orchestrator, poc-orchestrator, release-manager). Since T667 no agent holds the whole `gitlab` server, so every `true` entry is a named tool and you can still override only the tools an agent holds; a tool that no agent holds, such as `gitlab_merge_merge_request`, stays denied in every generated agent file whatever your global rule says (`gitlab_*: false` comes first in each holder's map). No supported way through the generated files or through your project or global configuration keeps a prompt there (an `agent.<name>.permission` entry in your project config is also placed before the agent's own rules); only a source that Opencode loads after the agent files can, the environment variable `OPENCODE_CONFIG_CONTENT` (observed on opencode-ai 1.19.2) and, by source reading only, the managed configuration (SEC-T657-04, SEC-T663-03; `docs/artifacts/mcp-agent-denials-evidence-v1.md`). The `<server>_*` wildcards also match a user-owned server whose cleaned name starts with that prefix and an underscore (a server `gitlab_ee` is matched by `gitlab_*`, `gitlab-ee` is not); for an agent without the server that fails closed. Saved "always" approvals do not undo a deny: the legacy runtime hides a tool whose last matching rule is a deny, and the current core tests `denied()` before it adds saved approvals (source reading; an approval saved before the deny existed is unverified). Opencode's built-in agents (build, plan, general, explore, ...) and agent files of your own get no per-agent deny and no global GitLab deny; only the server-level `permission` of `.opencode/opencode.json` (the six Playwright tools) applies to them, so every other tool of every configured server, GitLab included, remains reachable through them. That gap is a decision of the user (2026-10-16, "No, document the gap only") and is tracked. A user-owned `playwright-local` entry is another server name and is not denied by either list. `install.sh --update` keeps your own `permission` and `excludeTools` entries (it unions the lists and keeps your rules) and puts the generated denial back; evidence: `docs/artifacts/mcp-server-denials-v1.md` (recorded before Cursor was removed; its Cursor rows are historical).

## Optional (extended MCP servers)
- **uv** (provides `uvx`) — launches the `git` server (`uvx mcp-server-git@<pinned version>`). Install from <https://docs.astral.sh/uv/>.

- **`poc-security-audit` server (PoC security scan; optional)** — needs Python `mcp==2.2.0` (`pip install -r implementation/runtime/security/requirements-mcp-server.txt`, in a virtual environment that the `python3` your assistant launches can use; the installer prints the command) and **Git 2.40 or newer** on `PATH`: an older git makes every call fail closed as `git_failed`. Its config is generated for every platform except GitHub Copilot (Claude Code also needs an allow rule in your own `.claude/settings.json`). Setup steps: the "Optional: the PoC security scan server" section of `README.md`.

Start your assistant from the project root. The `filesystem` (`.`) and `git` (`--repository .`) servers resolve the path against the launch directory; Cline's configuration is global, so use an absolute path there. The `filesystem` server can read every file in the workspace, including `.env*` files and `.git`, and the `git` server exposes write tools.

### Pin-bump policy
MCP servers launched via `npx` or `uvx` are pinned to exact versions in `implementation/knowledge/mcp/servers.yaml` (audit SEC-002); do not replace a pin with `@latest` or a range. The devops-engineer bumps the pins at every release and at least monthly; there is no automated scheduler. Each bump is a reviewed change that edits `servers.yaml` and the `APPROVED_NPX_PINS` dict in `tests/functional/test_mcp_package_pins.py` together. Before a bump, check the package with `npm audit` or OSV, and check the registry's latest version and provenance. `@zereight/mcp-gitlab` holds the GitLab token, has a single maintainer, and releases often with published advisories, so it is reviewed at every release. The flags of the `playwright` entry (hardening and `--blocked-origins`) are part of the approved form: a bump of `@playwright/mcp` re-checks them against the new version's `--help`, re-checks the browser revision, and updates the pinned flags test.

**Checklist (T676).** The step-by-step pin-bump and release verification checklist (npm provenance, `scripts/audit-mcp-pins.py` audit path, manual advisory read for the three reference servers, browser security-version check, blocked-origins re-check, Python hash locks, container provenance, and the one-time live checks of the Gemini and Opencode denials) is `docs/wiki/mcp-pin-bump-checklist.md`. The hash-locked Python sets are `implementation/runtime/*/requirements-mcp-server.lock.txt`: `pip install --require-hashes -r <lock>` installs exactly the audited set.

### Upgrading from v7.x
After `scripts/install.sh --update`, the `filesystem`, `git` and `supabase` entries are overwritten in place. The `github` server (a container) is no longer shipped (v9.0.0, user decision 2026-10-22): the update removes the generated `github` entry from an installed config when its `.provenance.json` sidecar lists it; if you used it, keep a hand-copied entry under your own server name first (for example `github-mine`). The `playwright` entry is hardened and needs Chrome for Testing (above). The `docker`, `postgresql` and `fetch` servers (`fetch`: audit SEC-T646-01) are removed from the generated configs; the update drops them from an installed config only if its `.provenance.json` sidecar lists them. Otherwise remove them by hand or with `python3 scripts/merge-mcp-json.py --source <generated file> --dest <your file> --force-prune-keys <name>`, run once per name and per file (`install.sh` does not pass this option). Use the per-name form: the combined `--force-prune-keys docker,postgresql,fetch` refuses and writes nothing if any one of the names is already gone from that file, which is the usual case after a partial clean-up. The `fetch` name alone is `--force-prune-keys fetch`. A server entry of your own named `docker`, `postgresql` or `fetch` is removed too if the old sidecar lists those names. A run without a sidecar writes one that does not list them, so later automatic pruning cannot remove them. Client approval for the changed servers may be requested again. Full steps: `docs/wiki/mcp-servers.md`.

### GitLab token

The `gitlab` MCP server (`@zereight/mcp-gitlab@2.2.5`) needs one GitLab credential. Use a **dedicated credential for the harness**: never your own `glab` or git token. Every agent that holds a shell (`execute`) runs as you and can reach whatever token the server uses (SEC-T660-01), so the credential must be weak enough that its theft is no worse than the tool list you grant. Design and evidence: `docs/artifacts/gitlab-token-handling-design-v1.md`; the user's decision of 2026-10-16 is recorded in `docs/plans/plan-123-post-release-follow-ups.md`. Every statement below is documentation or vendor source read on 2026-10-16; **no statement was observed in a live run** unless it says so, and the three live checks at the end are yours to run.

#### Scope and role

This is the only scope table; the wiki points here. The two earlier lists (one here, one in the wiki) were wrong: a token with only `read_api`, `write_repository` and `read_user` cannot create an issue or a note, because `read_api` is read-only and `write_repository` does not authenticate against the REST API; the wiki's list asked for repository scopes that no role needs.

| Use | Examples | Scope | Minimum role (GitLab permissions page) | Fine-grained permission rows |
|-----|----------|-------|----------------------------------------|------------------------------|
| Read issues, notes, labels, milestones, issue links, members | `list_issues`, `get_issue`, `list_labels` | `read_api` is enough | Guest | Issue / Issue note / Label / Milestone / Issue link / Member: Read |
| Read merge requests, pipelines, jobs, job traces | `get_merge_request`, `list_pipelines`, `get_pipeline_job_output` | `read_api` is enough | Guest (pipeline visibility needed) | Merge request / Pipeline / Job: Read |
| Create an issue, a note, an issue link | `create_issue`, `create_issue_note` | `api` | Guest | Issue / Issue note / Issue link: Create |
| Update an issue; create or edit labels and milestones | `update_issue`, `create_label` | `api` | Planner (labels and milestones: not confirmed, unverified) | Issue: Update; Label / Milestone: Create, Update |
| Create a merge request, a branch, a tag | `create_merge_request`, `create_branch` | `api` | Developer | Merge request / Branch / Repository tag: Create |
| Push files or a commit | `push_files`, `create_or_update_file` | `api` | Developer (unprotected branch), Maintainer (protected) | Repository file / Commit: Create |
| Trigger, retry or cancel a pipeline | `create_pipeline`, `retry_pipeline` | `api` | Developer | Pipeline: Create, Update; Job: Run |
| Merge a merge request | `merge_merge_request` | `api` | not found on the permissions page (unverified); depends on "allowed to merge" of the protected branch | Merge request: Merge |
| Create a release, protect a tag | `create_release` | `api` | Maintainer | release-create row not found (unverified) |
| Delete anything, unprotect a branch | `delete_branch`, `unprotect_branch` | `api` | varies | Delete rows |

Rules that follow from the table:

- **The roles that write need `api`, and nothing else.** `qa-engineer` and `scrum-master` create and update issues, notes, labels and milestones, so a read-only token makes them fail. Do not add `write_repository`, `read_repository`, `ai_features`, `sudo`, `admin_mode`, `read_user` or any other scope: `scripts/check-gitlab-token.py` warns on every scope beyond `api`, `read_api`.
- **The role sets the ceiling, not the scope.** An `api` token of a Planner or Reporter identity does not reach the push and merge-request rows of the table (the merge row itself is unverified; branch creation: unverified); the same scope on a Maintainer account can do everything. Limit by role, never Maintainer or Owner. With the named tool sets of T666 and T667 (merged; names compared with this table on 2026-10-22, not run): `qa-engineer`, `scrum-master`, `devops-engineer` and `poc-devops-engineer` need at most Planner or Reporter (issues, notes, labels, milestones, read-only lookups, CI lint); `orchestrator`, `poc-orchestrator` and `release-manager` hold `create_merge_request`, which needs **Developer**. One shared token therefore needs Developer if you use those three roles, Planner or Reporter otherwise. No role holds merge, push, branch or tag creation, release creation, pipeline trigger or delete tools.
- **A Developer-level `api` token is more than a merge-request token (SEC-T665-07).** It can push commits to branches that are not protected, create tags that no protected-tag rule covers, and start pipelines on those branches. A pipeline on a branch the token holder controls runs that branch's `.gitlab-ci.yml` on your runners, with every unprotected CI/CD variable and the job token, whatever the agents' tool lists say. Branch protection on `main` and `develop` does not stop this: it protects those branches, not the runners. Whether a Developer token can also push or merge to protected branches depends on the "allowed to" settings of each branch (unverified). Limit it with protected variables, protected environments, runners restricted to protected refs and a dedicated low-privilege project: these are your GitLab configuration, outside the harness. The permission rows are those of the GitLab permissions page as read on 2026-10-22 through a fetch tool that flattened its tables (two rows, tag creation and job cancel, were marked "inferred" by that tool); the chain as a whole was not run **(unverified)**.
- **The token is not per role, and a token per role is not offered.** There is one `gitlab` entry. If you use `orchestrator`, `poc-orchestrator` or `release-manager`, the one token is Developer-level, and every agent with `execute` runs as you and can read it, whether or not it holds a GitLab tool (see "What this does not protect" below). `scrum-master` holds no shell (its tool line has no `execute`). The user decided on 2026-10-22 ("A: status quo + exposure sentence (Recommended)"; option A of the T681 design, `docs/artifacts/gitlab-per-role-token-design-v1.md`) to keep one token and document this exposure; two server entries, no MCP merge-request creation and per-role tokens were not chosen. On a maintainer's machine the `glab` and git credentials are usually stronger than this token (see "What this does not protect"); for an adopter without them, this token is the strongest. For a lower-privilege token, see "Reporter profile" below.
- **Expiry at most 90 days**; rotate; revoke the old token when you rotate. No token without an expiry.
- **Server-side branch protection is a second line outside the harness**: protect `main` and `develop` and restrict merging to Maintainers, so a Developer-level token cannot merge or push there (whether it can is live check 5 of the design, unverified). Without that protection no such line exists.

#### Reporter profile

A supported mode for adopters who want a lower-privilege token and can do without merge requests opened through MCP. The user decided on 2026-10-22 (T681, AskUserQuestion): "A: status quo + exposure sentence (Recommended)" and, for the profile, "Yes, document it (Recommended)". Source: `docs/artifacts/gitlab-per-role-token-design-v1.md`, sections 6 and 8.

- **What it is.** Use a token whose role in the project is Planner or Reporter (scope `api`, expiry at most 90 days, as in "Token type" below) instead of a Developer one. The role holds per project: a personal access token of a user who is Developer or Maintainer in other projects has that role there, so only a project or group access token, or a dedicated user whose only membership is the target project, bounds the reach to that role. Nothing is installed or regenerated: replace the token by the steps of "Migration from v8.0.0" below (create the scoped token, write it to the mode 0600 file, remove the old export, run `scripts/check-gitlab-token.py`, revoke the old token).
- **What stops working.** `orchestrator`, `poc-orchestrator` and `release-manager` hold `create_merge_request`, the one tool that needs Developer (table above). With a Planner or Reporter token a `create_merge_request` call fails with an authorization error from GitLab **(unverified: documented reading of the permissions page, not run; the exact error is not recorded)**. Those roles then hand the merge request to the top-level session, which opens it with your own credential; this is consistent with the existing policy that the top-level session merges, tags and releases. The agent files are not changed for this profile, so how an agent reacts to the failed call is unverified.
- **What keeps working.** Every other tool of the seven GitLab roles is within the ceiling of the table: reads need Guest (pipeline and job reads need pipeline visibility); creating an issue, a note or an issue link needs Guest; updating an issue and creating labels and milestones need Planner (the label and milestone rows are unverified, see the table). So `qa-engineer` works with Reporter, and `devops-engineer` and `poc-devops-engineer` do for the tools in the table (their CI lint tools are not in the table; their minimum role is unverified); `scrum-master` needs Planner for its update, label and milestone tools. This reads the minimum-role column of the table and was not run.
- **What the role ceiling gives you.** On the GitLab permissions page as read on 2026-10-22, pushing code needs Developer (a Reporter cannot push), and the rows for creating a merge request, tags and pipelines are Developer rows of the table above. So the Developer-level reach described above is not part of a Planner or Reporter token. Where the page is silent the cell stays unverified: the merge row, the label and milestone rows and the release row of the table are marked so, and whether a Planner or Reporter token can create a branch is not established here **(unverified)**. The chain as a whole was not run.
- **It is not a read-only token.** A Planner or Reporter `api` token still reads the whole project (code, issues, merge requests, and job logs where they are visible to that role), writes issues and notes, and can use any endpoint its role allows. Only the role limits it, not the scope.
- **What it does not change.** Every agent with `execute` can still read the token (see "What this does not protect" below), and the SEC-T660-01 residual stays: mitigated, not closed. The maintainer's `glab` and git credentials are untouched. The profile lowers what the harness-issued token can do; it does not hide it.

#### Token type

Preference order today (the fine-grained token moves to the first place only after live check 1 below passes):

1. **Project or group access token** with role Planner or Reporter (Developer only if a role creates branches or merge requests) and scope `api`. It is a bot user and cannot reach other projects. GitLab.com: Premium or Ultimate; self-managed: any licence. Documented, unverified in this harness.
2. **Personal access token with scope `api` of a dedicated low-role user** whose role in the project is Planner, Reporter or Developer. Works on every tier. Documented, unverified in this harness.
3. **Fine-grained personal access token** (GitLab 19.2 or later, GA; Free, Premium and Ultimate), limited to the project, with exactly the permission rows of the table. It is the smallest credential and **becomes the first choice once the user has run live check 1 and it passes**; until then it is **unverified**: it is not known whether all 44 tool calls of `qa-engineer` and `scrum-master` succeed with it (the pinned server may use GraphQL or endpoints that a fine-grained token covers only in part), or whether single projects can be selected in the creation form.

Never use a token with `write_repository`, `admin` or `sudo`. A service account is not researched (unverified).

#### File mode

File mode is the documented default for new installs; the environment mode (an exported `GITLAB_PERSONAL_ACCESS_TOKEN`) stays supported. The pinned server reads `GITLAB_PERSONAL_ACCESS_TOKEN_FILE` once at start, so the token is in no process environment: not in the environment of the assistant, of its shell commands or in `/proc/<pid>/environ`, and not in a shell history.

1. Create the file outside every project, readable by you only (bash). The subshell keeps `umask` from leaking into your session, `: >` creates the empty file and `chmod 600` fixes the mode before the token is written; the server performs no mode, owner or symlink check, `scripts/check-gitlab-token.py` does:

   ```bash
   ( umask 077; mkdir -p "$HOME/.config/gitlab-mcp"; : > "$HOME/.config/gitlab-mcp/token"; chmod 600 "$HOME/.config/gitlab-mcp/token" )
   read -rsp 'GitLab token: ' t && printf '%s' "$t" > "$HOME/.config/gitlab-mcp/token"; unset t
   ```

   Run the checker afterwards (step 6): it refuses a symbolic link, a FIFO, a file you do not own and a non-ASCII token, and warns about a mode wider than 0600. Not inside the project directory: the extended `filesystem` server can read every file under the launch directory.

   Where the file lives is your decision; the harness stores nothing and sends the token nowhere but to GitLab. The example above assumes **full-disk encryption on the workstation** (the file is a plain file at rest). Better placements, if you can: a file under `$XDG_RUNTIME_DIR` (a tmpfs owned by you, removed when your last session ends unless lingering is on, so nothing is written to the file system (tmpfs can still be swapped unless swap is encrypted); you write the token into it again after each login), or a file that you fill from your keyring at login (for example `secret-tool lookup ... > "$XDG_RUNTIME_DIR/gitlab-mcp-token"` with the same mode). A same-user process can run the same lookup, so these reduce what is left on disk, not who can read it (see "What this does not protect").
2. Export the **path**, not the token (a path is not a secret), in the environment that starts the assistant: `export GITLAB_PERSONAL_ACCESS_TOKEN_FILE="$HOME/.config/gitlab-mcp/token"`.
3. Then **remove the old export** of `GITLAB_PERSONAL_ACCESS_TOKEN` from your shell profile and your environment. A non-empty `GITLAB_PERSONAL_ACCESS_TOKEN` wins over the file; the server only prints a warning, so a stale export silently keeps the old, broader token in use.
4. Claude Code: leave the generated `${GITLAB_PERSONAL_ACCESS_TOKEN:-}` and `${GITLAB_PERSONAL_ACCESS_TOKEN_FILE:-}` as they are. Claude Code passes an unset `${VAR}` through as the literal text `${VAR}`, which is non-empty and would win over the file; the `:-` (empty default) prevents that. `install.sh --update` restores the generated form if you edit it. The empty default is documented Claude Code syntax but **unverified** (live check 3).
5. Other clients: where an unset reference stays literal text (verified in the vendor source for Cline; unknown for VS Code), also `export GITLAB_PERSONAL_ACCESS_TOKEN=` (set, empty). Not on Pi: Pi fails the whole server for an unset **or empty** variable (observed, Pi 1.4.0), so the generated Pi entry leaves the two optional variables out and the server reads them from Pi's environment; export only the one you use. Gemini CLI and Opencode resolve an unset variable to an empty string (documented).
6. Check the token: `python3 scripts/check-gitlab-token.py` from an emage.code checkout (standard library only; prints findings and never the token; exit 0 ok, 1 warnings, 2 error). It reads the same sources as the server (a non-empty variable first, else the file), asks `GET /personal_access_tokens/self` and `GET /user`, sends the token only to an https host that you pin (`--expected-host`, else `CI_SERVER_HOST`, else `gitlab.com`) and refuses redirects. It warns on a scope beyond `api`, `read_api`, on a missing expiry or one beyond 90 days, on an administrator owner, on a role above Developer when a response carries one and on a token file readable by group or others. **It does not check the role in the usual case**: the two endpoints are not documented to report it (unverified), so it prints `role: NOT checked ... verify Planner, Reporter or Developer in the project's Members page` and ends with `result: ok (scope, expiry and owner only; the role was not verified)` (exit 0); only a role that was reported and is too high is a warning (exit 1). It refuses a token file that is a symbolic link, a FIFO or not owned by you, and a token that is not printable ASCII. Then run `claude mcp list` (or the client's equivalent).

#### What this does not protect

The token is the credential of one GitLab identity. After this change the **environment path** is mitigated, not closed:

- **Same user.** An agent that holds a shell runs as you. It can read the token file (file mode), the profile file that holds the `export` (environment mode), your shell history, and the other credentials of the same user: `~/.config/glab-cli`, `~/.git-credentials`, `~/.netrc`, SSH keys, `GITHUB_PERSONAL_ACCESS_TOKEN`. The `glab` token is usually the more powerful one. File mode removes the token from the process environment and from `/proc`; on Claude Code, under the posture above and once live check 2 passes, it also keeps it from sandboxed Bash and denied `Read`. It does not stop a same-user process from reading a file the client does not deny. On every other client no mechanism exists, and the role and scope table above is the only control.
- **Tool lists** are not enforced on Opencode and Gemini CLI (K-15), so a narrowed role can still call any tool of the server there. `GITLAB_PERMISSION_MODE` (below) is enforced by the server on every client.
- **Pi has no per-server environment scoping.** Every stdio server that Pi starts receives everything that is exported to Pi (observed in the T680 runs: a variable exported to Pi reached a server whose entry did not name it). It is a platform limit and part of SEC-T660-01.
- **The only closure** is an isolated user, container or VM that holds only the scoped credential and no `glab` or git token; the harness cannot create it.

The user re-accepted this residual on 2026-10-16 ("Adopt D and re-accept the residual (Recommended)"); the Security Engineer grades it in the T665 review (SEC-T660-01).

#### Server-side limits

The generated `gitlab` entry sets `GITLAB_PERMISSION_MODE=modify` (a literal, non-secret value). The pinned server then refuses every delete tool and the teardown tools such as `cancel_pipeline`, `stop_environment` and `unprotect_branch` (the teardown list is from the README on main; not matched to 2.2.5, unverified), on every client, **including your own session in that client**. It does not stop a shell that holds the token from calling the API directly (`curl`), and it does not narrow create, update, push or merge tools. To lift it, edit the entry in your own client config; `install.sh --update` writes the generated value back.

The pinned server reads five operator controls from its environment. The generated entry sets only the first; add any other to the `env` of your own `gitlab` entry in your client config (Opencode names that map `environment`). `install.sh --update` keeps a key that you add inside a generated entry (pinned by a test for `GITLAB_TOOLS` and `GITLAB_DENIED_TOOLS_REGEX`). **Nothing here was run.** Only these statements were confirmed against the README of the pinned `@zereight/mcp-gitlab@2.2.5` (security review of T674): `GITLAB_PERMISSION_MODE` takes `readonly`, `modify` or `full`; `GITLAB_DENIED_TOOLS_REGEX` is a "deny-list by pattern" with no syntax given; `GITLAB_ALLOWED_PROJECT_IDS` "is checked only for `/projects/:id` paths"; an explicit `GITLAB_TOOLS` list replaces the default `core` toolset and does not merge with it; `GITLAB_READ_ONLY_MODE` is deprecated. Every other statement in the table was read on the README of the GitHub main branch (through a web-fetch summary, 2026-10-22) and is marked **(README on main; not matched to 2.2.5, unverified)**. Check any marked point against your own server before you rely on it.

| Variable | What the README says it does | Limits and unverified points |
|----------|------------------------------|------------------------------|
| `GITLAB_PERMISSION_MODE` | `readonly`, `modify` or `full`. Per the README on main: default `full`; `modify` allows create and update, blocks delete tools and the teardown tools it lists (`cancel_pipeline`, `stop_environment`, `unprotect_branch`) and destructive mutations through `execute_graphql` and the `delete` and `move` actions of `push_files`; for `gitlab_api_request`, readonly allows GET and modify rejects DELETE **(README on main; not matched to 2.2.5, unverified)** | Set to `modify` by the generated entry. | `GITLAB_DENIED_TOOLS_REGEX` | A "deny-list by pattern" for tools | The README gives no syntax, case rule or match target (unverified); test a pattern against a scratch project before relying on it. Whether it covers `gitlab_api_request` is unverified (that tool is off unless `GITLAB_TOOLSETS` lists `api`, per the README on main **(not matched to 2.2.5, unverified)**) |
| `GITLAB_ALLOWED_PROJECT_IDS` | A project allow-list, "checked only for `/projects/:id` paths" | Endpoints such as `/search`, `/users`, `/groups/:id` and `/runners` are not constrained, and `GITLAB_PROJECT_ID` and OAuth group allow-lists are not enforced for `gitlab_api_request` **(README on main; not matched to 2.2.5, unverified)**. A list that omits a tool a role needs, or `discover_tools`, makes that tool unavailable to every agent in the session; how it interacts with `discover_tools` is unverified |

`GITLAB_READ_ONLY_MODE` is deprecated in the README in favour of the permission mode `readonly` (the generated entry uses `modify`, not `readonly`); the README on main announces its removal in the next major version **(README on main; not matched to 2.2.5, unverified)**. All five are server-side limits, enforced on every client. None of them stops a shell that holds the token from calling the GitLab API directly, and none narrows `create_merge_request`, which can target any project the token reaches.

#### Migration from v8.0.0

1. Run `scripts/install.sh --update`. The `gitlab` entry gains `GITLAB_PERSONAL_ACCESS_TOKEN_FILE` and `GITLAB_PERMISSION_MODE`; on Claude Code the token placeholders gain `:-`; on Gemini CLI every placeholder changes from `${env:VAR}` to `${VAR}`. Your own env keys in the entry are kept, a literal value you typed into a generated key is replaced by the generated placeholder (**not on Pi**, see below). Claude Code asks you to approve the changed project-scoped server again. On Pi (T680) every placeholder changes from `${env:VAR}` to `${VAR}`, and `install.sh --update` also drops the old `GITLAB_PERSONAL_ACCESS_TOKEN` and `GITLAB_PERSONAL_ACCESS_TOKEN_FILE` entries of the `gitlab` server in `.pi/mcp.json` (their `${env:...}` text was passed to the server as the literal value on Pi, so they never worked); the update prints "dropped the retired ${env: entry" with the key names and, once, a hint that the dropped keys held placeholder text. Your other keys are kept, **including a token you pasted into `.pi/mcp.json` as a literal value**: the generator no longer ships those two keys on Pi, so the merge cannot replace them. The update prints `WARNING: ... holds a literal value; remove it from the file and revoke the token` (the key name, never the value) for any key of yours with a credential-like name (TOKEN, KEY, SECRET, PASSWORD, AUTHORIZATION) and a literal value, on every platform. Remove it from the file by hand, revoke that token and use File mode. `hindsight` and `cwso` are no longer generated for Pi (below): the update prunes the entries that an older release generated and says so ("pruned the retired generator server"); entries of your own under other names are untouched. **If you edited `hindsight` or `cwso` in place, copy the entry to another name before updating; the update removes those two names from `.pi/mcp.json`.** When a pruned entry holds a literal value where the generator writes a `${NAME}` reference, the update says the entry "differs from the generated entry; its old content is not kept" (names only; the judgement is a heuristic, because the old generated entry is not available).
2. Nothing breaks if you do nothing: the exported `GITLAB_PERSONAL_ACCESS_TOKEN` keeps working, and the risk stays as documented in K-16.
3. To adopt file mode: create the scoped token (table above), write it to a mode 0600 file outside every project, export the path, **remove the old export** from your shell profile and environment, run `scripts/check-gitlab-token.py`, then **revoke the old, broader token**: it has been in a profile file and in process environments.
4. Existing installs and the repository root keep the old rendering until the next `--update` or `--projections-only` refresh. Rolling back to the v8.0.0 files restores the old entry; the token file is then simply unused.
