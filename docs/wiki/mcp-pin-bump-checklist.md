# MCP pin-bump and release verification checklist

Maintained by the devops-engineer; a Security Engineer reads each bump. Origin: T676 (register items SEC-T646-03, -04, -05, -06, SEC-T655-06, -07, SEC-T658-02, SEC-014, T638-L-2, -8, K-17, K-20, SEC-T675-03, -09; review follow-ups SEC-T676-01 to -10). The `github` MCP container (T638-L-3) is no longer shipped (v9.0.0, user decision 2026-10-22), so it has no section here. Based on: `docs/artifacts/tracked-debt-register-v1.md`, `docs/artifacts/security-review-t675-ci-release-hardening-v1.md`. The short policy stays in `implementation/PREREQUISITES.md` ("Pin-bump policy") and `docs/wiki/mcp-servers.md` ("Pin maintenance"); this page is the procedure behind it. Keep it current: a bump that changes a step edits this page in the same merge request.

Anything marked **(unverified)** was not observed in a live run.

## 1. Every bump of an `npx` pin (`servers.yaml`)

Run from the repository root. `npm`, network access and `python3` with PyYAML are needed.

1. **Read the pins and the registry state.** `python3 scripts/audit-mcp-pins.py list`, then `python3 scripts/audit-mcp-pins.py provenance` (pinned version and `latest`, provenance yes/no).
   **Minimum release age (SEC-T860-01).** Pin a version only once it is at least **7 days** past its npm publication time (`npm view <pkg>@<new> time --json`, the entry for `<new>`): a compromised release is usually found and unpublished within days. Check every pin with `python3 scripts/audit-mcp-pins.py age` (exit 1 names each pin younger than `--min-age-days`, default 7; a missing or unparseable publication time is an error, exit 2, never "old enough"). A younger pin needs a recorded exception in the merge request that names three things: its provenance (step 2), its audit result (step 3) and its diff review (`npm diff` against the previous pin, read for new network, process or file access). Pass each exception to the check as `--allow-young <pkg>@<version>:<reason>` (repeatable; it must name a current pin, so a bump voids it), and keep the list below current. Recorded exceptions (both pins predate this rule; each stops being needed once the pin is 7 days old):
   - `@modelcontextprotocol/server-filesystem@2.4.0`, the first exception: published 2026-11-18, pinned 2026-11-19 (T859). Reasons (T860, `docs/artifacts/security-review-t860-batch-x-v1.md`): SLSA provenance v1, a clean audit, the diff was read, and it is an opt-in server that no agent holds. Check: `--allow-young @modelcontextprotocol/server-filesystem@2.4.0:T860 provenance, clean audit, diff read, opt-in server no agent holds`.
   - `@brave/brave-search-mcp-server@2.1.5`: published 2026-11-17, pinned 2026-11-19 (T851). Reasons (the T851 row of section 5): the first brave version with SLSA provenance v1, a clean audit with `--signatures` and no `--accept`, the diff and the extra review were read, and the bump retired seven high advisories of 2.1.4. Check: `--allow-young @brave/brave-search-mcp-server@2.1.5:T851 provenance, clean audit, diff read`.
2. **Provenance preference (SEC-T646-03, T638-L-8).** Pin the newest version that has an npm provenance attestation (`dist.attestations.provenance`). If the newest version has none but an older one has, pin the newer only with a written reason in the merge request. If the package has never published provenance, record the exception and do the extra review below. State on 2026-10-22: provenance present for `@zereight/mcp-gitlab`, `@playwright/mcp`, the three `@modelcontextprotocol/server-*` packages and `@supabase/mcp-server-supabase`; **absent, and absent from every published version, for `@brave/brave-search-mcp-server` and `toolradar-mcp`** (exceptions). Since 2026-11-19 (T851) that holds for the brave versions up to 2.1.4 only: the pinned `@brave/brave-search-mcp-server@2.1.5` (published 2026-11-17) is the first brave version with a provenance attestation (SLSA provenance v1); keep the extra review below for it anyway, as for every brave bump.
   Extra review for a package without provenance, or with a single maintainer (`@zereight/mcp-gitlab`, `toolradar-mcp`, `@brave/brave-search-mcp-server`): `npm view <pkg>@<new> maintainers scripts.install scripts.postinstall dependencies --json`, `npm diff --diff=<pkg>@<old> --diff=<pkg>@<new>` read for new network, process or file access, and the unpacked size against the previous version (`toolradar-mcp` ships a 750 KB bundle that a diff does not make readable: treat a size jump as a reason to hold the bump). The scripts run with `--ignore-scripts` in the audit, so an install script is read, never executed, by the audit.
3. **Audit (SEC-T646-05, K-17).** `python3 scripts/audit-mcp-pins.py audit --audit-level low`. The audit fails closed (a reply without both `vulnerabilities` and `metadata` is an error; an unknown severity counts as critical) and runs npm with an empty user and global `.npmrc` and `--registry https://registry.npmjs.org/`. It writes a throwaway `package.json` from the pins into a temporary directory, resolves it with `npm install --package-lock-only --ignore-scripts` and runs `npm audit`. Add `--signatures` for a full `--ignore-scripts` install and `npm audit signatures` (registry signatures and provenance of the whole tree). Exit 1 means a finding at or above the level: record it in the merge request with the applicability to stdio use, or do not bump. A finding the user has accepted is passed as `--accept GHSA-xxxx-xxxx-xxxx:YYYY-MM-DD:<package>@<version>` (repeatable; the expiry date and the package are mandatory; SEC-T676-11: the package@version must be a current pin of `servers.yaml`, so a bump of that pin voids the acceptance; the date may not be more than 90 days from the day of the run; the acceptance counts only when that package is the only pinned package the vulnerable library entry puts at risk, so a second pin that pulls the same library stays a finding; an accepted advisory is still printed as ACCEPTED and an expired acceptance fails the run); every acceptance needs an artifact. None is needed today (T851, 2026-11-19). The last ones were the seven of `docs/artifacts/brave-audit-acceptance-v4.md` (seven advisories of the then-pinned `@brave/brave-search-mcp-server@2.1.4`, six on `@modelcontextprotocol/sdk@1.30.0` and one on `zod@4.3.6`, expiry 2027-01-30 or the next brave release; the user's acceptance of 2026-11-12 for v11.0.0 only). They ended with the bump to `@brave/brave-search-mcp-server@2.1.5`, which depends on `@modelcontextprotocol/sdk@1.32.2` and `zod@4.6.7` and has no finding at any level; the bumped pin voids them, and the script refuses them (`is not a current npm pin`, exit 2). A pinned package counts as put at risk when npm lists it in the library entry's `effects` or names the library in its own `via` (T712: npm 11.17.0 fills `effects` for only one of two vulnerable dependencies of a package). `python3 scripts/audit-mcp-pins.py generate DIR` writes the same manifest (and `requirements-uvx.txt`) if you want to run other tools on it.
4. **Manual advisory read for the three reference servers (SEC-T646-06).** `@modelcontextprotocol/server-memory`, `-sequential-thinking` and `-filesystem` moved from calendar versions (`2025.x`, `2026.x`) to `1.0.0` (published 2026-10-11) and to `2.0.0` (2026-10-19). Semver sorts the calendar-form advisory ranges above `1.0.0` and `2.0.0`, so `npm audit` can over- and under-report. For each: open the GitHub Advisory Database (ecosystem npm) for the package, read every advisory's affected range and fix date, and decide whether the pinned version is affected by date and by changed code, not by the sorted range. To list the registry's own advisories for probe versions: `POST https://registry.npmjs.org/-/npm/v1/security/advisories/bulk` with `{"<pkg>": ["0.0.1", "<a calendar version>", "<the pin>"]}`. Record the date and result in section 5.
5. **Edit the pin** in `implementation/knowledge/mcp/servers.yaml` and in `APPROVED_NPX_PINS` of `tests/functional/test_mcp_package_pins.py` together, run `node implementation/scripts/sync.mjs --root implementation` and `python3 implementation/scripts/generate-registry.py`, and declare the projection drift as usual.
6. **Playwright only.** (a) Re-check every flag against `npx -y @playwright/mcp@<new> --help`. (b) **Browser security version (SEC-T655-06):** the browser is patched only at a pin bump. Install it with `npx -y @playwright/mcp@<new> install-browser chrome-for-testing`, read its version (`~/.cache/ms-playwright/chromium-<revision>/.../chrome --version`, or the revision's `browsers.json` entry) and compare it with the current Chrome for Testing Stable (`https://googlechromelabs.github.io/chrome-for-testing/last-known-good-versions.json`, field `channels.Stable.version`). Rule: do not accept a bump whose browser is more than one major behind Stable, and treat a Stable release that fixed an exploited-in-the-wild Chrome vulnerability (Chrome releases blog, CISA KEV) after the bundled version as a blocker for the bump; if no newer `@playwright/mcp` exists, record the delay and decide with the Security Engineer. State on 2026-10-22: bundled Chrome for Testing 155.0.8059.12 (0.0.83), Stable 156.0.8078.47, one major behind, `@playwright/mcp` latest is 0.0.83. Update the browser version in `implementation/PREREQUISITES.md`. (c) **Blocked-origins re-check (SEC-T655-07):** the list is a glob list the package turns into `*://<entry>/**` patterns (`originOrHostGlob` and `globToRegexPattern` in `playwright-core/lib/coreBundle.js`). After any change re-run the matcher on a sample of URLs that must be blocked (metadata names, `168.63.129.16`, `192.0.0.192`, `198.18.0.1`, multicast, NAT64 `[64:ff9b::...]`, 6to4 `[2002:...]`, wildcard-DNS names such as `127.0.0.1.nip.io`) and that must stay allowed (`example.com`, `internal.example.com`, `192.0.2.1`). `tests/functional/test_blocked_origins_matcher.py` holds those samples and a port of the vendor function; set `PLAYWRIGHT_CORE_BUNDLE=<install dir>/node_modules/playwright-core/lib/coreBundle.js` and it also runs the real vendor functions with `node` and requires the same answers (2026-10-22: 39 entries, the port and `playwright-core` of 0.0.83 agree on every sample). The 39-entry list is pinned by `tests/functional/test_mcp_package_pins.py`. Residual gaps, closed only by egress filtering and not by this list: DNS names that resolve to internal addresses and are not in the wildcard-DNS list or are not `*.`-subdomains of it (the apex names `localtest.me` and `lvh.me` ARE listed; the apex of `nip.io` and `sslip.io` does not resolve to a private address), Teredo addresses (`2001:0:...`, whose serialised form varies with zero compression, so no safe glob was added), redirects, WebSockets, a trailing-dot form of `*.internal.` / `*.local.`, IPv4-mapped forms other than `[::ffff:`.
7. Run the gates of the task brief and the full suite.

## 2. Python pins and hash locks (SEC-T646-04, SEC-014, T638-L-2, SEC-T675-09)

- **`uvx` pin** (`mcp-server-git`): `python3 scripts/audit-mcp-pins.py generate /tmp/pins` then `uvx pip-audit -r /tmp/pins/requirements-uvx.txt --no-deps --disable-pip`. PyPI has no npm-style provenance check here; read the release page.
- **Runtime requirement files** (`implementation/runtime/security/requirements-mcp-server.txt`, `implementation/runtime/memory/requirements-mcp-server.txt`): both pin `mcp==2.2.0` and carry the floor `httpx2>=2.12.0` (before 2.12.0: GHSA-8xx6-hgc6-gc2m). Next to each is `requirements-mcp-server.lock.txt`, the hash-locked complete set for Python 3.10 and later. Users who want integrity: `pip install --require-hashes -r implementation/runtime/security/requirements-mcp-server.lock.txt`. The two locks must be byte-identical (a test enforces it). Regenerate after any change of either input, from its own directory:
  `uv pip compile requirements-mcp-server.txt --universal --python-version 3.10 --generate-hashes --exclude-newer <UTC timestamp of the day> -o requirements-mcp-server.lock.txt` (`--exclude-newer` makes the run reproducible; the current locks use 2026-10-30T00:00:00Z and the date is in the file header; regenerated on 2026-11-13 with uv 0.11.9 and `--upgrade-package opentelemetry-api==1.45.2` for GHSA-mf5v-w3w3-f6cg, from the previous lock so that no other package changed; 1.45.2 was uploaded on 2026-10-29). **At the next regeneration (SEC-T676-14) set `--exclude-newer` to a timestamp seven days before the day of the run, not to the day itself**: a version published in the last week is then not locked, which gives the registry and the advisory feeds a cooldown to catch a hijacked or malicious release. The same applies to the CI locks below. Do not regenerate the locks only for this; take it when an input changes
  (`uv` is only needed by the maintainer; `pip-compile --generate-hashes` from pip-tools produces the same kind of file but resolves for one platform, so `uv --universal` is the reference). Then `uvx pip-audit -r <lock> --no-deps --disable-pip`.
- **CI lock files**: `ci/requirements-ci.in`, `ci/requirements-gate.in` and `ci/requirements-release.in` are the inputs of the `unit-tests`, `validation-super-gate` and `release-docs-gate` jobs; `ci/requirements-ci.txt`, `ci/requirements-gate.txt` and `ci/requirements-release.txt` are the locks (`uv pip compile ci/requirements-ci.in --universal --python-version 3.12 --generate-hashes --exclude-newer <UTC timestamp> -o ci/requirements-ci.txt`, same for the other two). The `--exclude-newer` timestamp is a cooldown (T730, SEC-T676-14): at least 7 days before the day you generate, never that day itself, and every new or changed package must be at least 14 days old (read its PyPI upload time); say so in the lock header. Regenerated on 2026-11-02 with `2026-10-22T12:00:00Z` and uv 0.11.9 (added `markdown-it-py==4.2.0` and `mdurl==0.1.2`, uploaded 2026-05-07 and 2022-08-14). `ci/requirements-release.txt` (T739) holds only those two packages, generated on 2026-11-05 with the same `--exclude-newer` and uv 0.11.9, for the parser of `scripts/verify-release-docs.py`. Its versions and hashes must equal those of `ci/requirements-ci.txt` (a test enforces it), so change the two locks together. Both wheels are pure Python (`py3-none-any`). `release-docs-gate` runs only in a tag pipeline, so no merge request pipeline proves this install: watch it in the next release or release candidate. The jobs run `pip install --require-hashes --only-binary=:all: -r ci/requirements-*.txt` (wheels only: an sdist would run its build backend inside the job; the line is a quoted YAML string because `:all: ` would otherwise parse as a mapping); `tests/functional/test_ci_hash_pins.py` fails on any other `pip install`, on a lock entry without a hash, on an input that is missing from its lock, and on a stale version. `mcp` in the CI lock must equal the pin in `requirements-mcp-server.txt`. After regenerating, the routine proof that the locks resolve on musl is the merge request pipeline (SEC-T786-02): `unit-tests` and `validation-super-gate` (and `release-docs-gate` in a tag pipeline) each install their lock with `--require-hashes --only-binary=:all:` in the pinned `python:3.12-alpine` image, and a lock that does not resolve or a changed version fails the job. An install check before pushing is a **maintainer-only step, on a Docker host that is not production, and never an agent step** (SEC-T786-02): the project's configured Docker host is a remote production host, so an agent does not run `docker` for this or for any other step of this page. For the maintainer, on a remote Docker host of that kind bind mounts do not work: stream the directory, `tar c ci | docker run --rm -i python:3.12-alpine@sha256:<pinned digest> sh -c 'mkdir /w && tar x -C /w && cd /w && python3 -m pip install --no-cache-dir --require-hashes --only-binary=:all: -r ci/requirements-ci.txt'` (done once on 2026-10-22: both locks install wheels-only in the pinned image, `import yaml, jsonschema, requests, pyarrow, cryptography, mcp` works; a changed version fails with a hash mismatch).

## 3. CI images and the pipeline (SEC-T675-03)

Only two bases remain: `node:24-alpine` (default image) and `python:3.12-alpine`. To bump one, read everything from the Docker Hub registry API, with no Docker: nothing is pulled into a container, extracted or run (SEC-T786-02; the method of `docs/artifacts/ca-check-t765-v1.md`, also used for the T785 bump). (a) Take an anonymous pull token from `https://auth.docker.io/token?service=registry.docker.io&scope=repository:library/<name>:pull` and send it with each request below. (b) `GET /v2/library/<name>/manifests/<tag>`, accepting the OCI index and Docker manifest-list media types, returns the multi-arch index: its digest is the pin, and the body must hash (sha256) to that digest. (c) From the index take the `linux/amd64` entry (the runner is x86-64), `GET /v2/library/<name>/manifests/<that digest>`, then its config blob and its layers with `GET /v2/library/<name>/blobs/<digest>`; hash each body against its digest. (d) The runtime version is in the config's `Env` (`NODE_VERSION`, `PYTHON_VERSION`). (e) The Alpine version is in the config's `history` (`ADD alpine-minirootfs-<version>-x86_64.tar.gz`) or in `/etc/alpine-release` of the base layer. (f) `apk-tools` and the other installed packages are in `/lib/apk/db/installed` of the top-most layer that holds that file (the last such layer in the manifest's `layers` list). Read the layers in memory with a tar reader (for example Python's `tarfile`): list the members and read those two files, extract nothing and execute nothing. Then re-read the `apk add` package versions in that Alpine branch's `APKINDEX`, and change digest and `~=` pins together in `.gitlab-ci.yml`. The proof of the Node that actually ran is the merge request pipeline's `verify-knowledge-drift` log: its `node --version` line must print the config's `NODE_VERSION` (T785: `v24.22.3`). End-of-life tags fail `tests/functional/test_ci_hash_pins.py` (Node 20 and below or an odd major, Alpine 3.21 and below, Python 3.9 and below, as of 2026-10-22: update the table when a line goes end of life). Digests in use: `node:24-alpine` `sha256:116b800c...` read 2026-11-11 (T785; Alpine 3.24.4, Node 24.22.3). `python:3.12-alpine` `sha256:e064671c...` read 2026-11-06 (T765; Alpine 3.24.4, Python 3.12.16), the same digest in every job. T676 first pinned both bases on 2026-10-22; `.gitlab-ci.yml` lines 13-21 hold the current record. The pipeline carries `# ci_images_reviewed_on: <date>` and `test_ci_hash_pins` fails when it is older than 120 days or older than the end-of-life table: re-read the digests, re-check the table, update both dates. The commands of the jobs were run once in these images on 2026-10-22 (`verify.mjs`, `sync.mjs` plus `git diff`, the markdown link check, the super gate with the locked packages, `verify-release-docs.py`); since then the pipelines have run these jobs, so that one-off run is history, not the proof. The per-bump proof is the merge request pipeline on the new digest: the two CA-chain jobs of the next paragraph and the `node --version` line of `verify-knowledge-drift` (SEC-T786-02).

**CA-chain check at every image bump (T766, SEC-T756-02, CVE-2026-115557).** `git` and libcurl in these images trust the image's CA store alone; OpenSSL has no denylist of the compromised eMudhra/emSign chains. At every bump of either digest, and of any `apk add` pin that can pull in a newer `ca-certificates`, the merge request's `ca-chain-check-python` and `ca-chain-check-node` jobs must pass. They run `scripts/check-ca-chains.sh` inside each pinned image against its own store: as shipped (copied before `apk add`) and after `apk add`, and in the python image also against the hashed directory `/etc/ssl/certs` (the node job runs that `--capath` check only when hashed entries exist, which today they do not, SEC-T768-03). Both jobs first run `sha256sum -c SHA256SUMS` in `tests/fixtures/ca-chains` (SEC-T768-02). Pass means: **0 of 16** chains of the disclosure and 0 of the 3 further crt.sh certificates on its keys validate (T767), no store certificate carries one of the 14 compromised keys (the disclosure's 12 and the 2 rollover keys of its chains; compared by SPKI, so a re-signed copy is caught; every PEM block that OpenSSL's loaders take as a certificate is read, `BEGIN CERTIFICATE`, `TRUSTED CERTIFICATE` or `X509 CERTIFICATE`, any other `BEGIN` type fails, and the certificates read must equal the blocks, SEC-T768-01), the fixtures pass their cross-check (16 chains, 3 extra certificates, 4 roots and 14 keys, each counted on its own, and every root, non-leaf chain certificate and extra certificate on a listed key, SEC-T768-02), the `gitlab.com` control validates, and `ca-certificates`/`ca-certificates-bundle` is release 20261020 or later (`--ca-release`; older releases still hold `emSign ECC Root CA - G3`, and 8 of the 16 chains validate). Every store run ends in `compromised chains and certificates validating: 0 of 19; controls validating: 1 of 1` and `RESULT: PASS`. A failing job blocks the bump: do not merge it, and report to the Security Engineer which chains validate. To run the check before pushing, take the bundle from the registry layers (no Docker; method in `docs/artifacts/ca-check-t765-v1.md`) and run `sh scripts/check-ca-chains.sh --cafile <bundle> tests/fixtures/ca-chains` with an OpenSSL 3 CLI. The chains, the control and their sources are listed in `tests/fixtures/ca-chains/README.md`. The check verifies at a fixed time (2026-11-07), so it does not start failing when the certificates expire.

**Release-gate runner at every bump of the tag jobs' image (T810, SEC-T741-17, plan-159).** The three tag-pipeline jobs (`release-docs-gate`, `main-develop-drift-gate`, `release`) carry `tags: ["release-gate"]`, so they need a runner with that tag; by the user's report only the dedicated project runner carries it (keep instance and group runners free of that tag, SEC-T811-04). That runner's `config.toml` allows one image: `allowed_images` holds the pinned `python:3.12-alpine@sha256:...` digest those jobs use. When that digest changes, the user must change `allowed_images` on that runner to the new digest in the same release, or the three jobs fail closed and nothing is published. An agent does not change the runner or its host. No merge request pipeline runs these jobs, so only the next tag pipeline proves it. The step, when the digest changes from `<old>` to `<new>`: in the release-gate runner's `config.toml` (by default `/etc/gitlab-runner/config.toml` in its LXC), in that runner's `[runners.docker]` section, replace the line `allowed_images = ["python:3.12-alpine@sha256:<old>"]` by `allowed_images = ["python:3.12-alpine@sha256:<new>"]`, then `gitlab-runner restart` (the runner also reloads a changed `config.toml` by itself; the restart makes it certain). A digest whose `linux/amd64` manifest is unchanged (as on 2026-11-19, when only the `riscv64` entry moved) need not be taken.

**Release-gate runner hardening (SEC-T811-05; user steps, an agent changes nothing on the runner or its host).** Option names verified on 2026-11-19 against GitLab Runner's documentation on `main` (https://docs.gitlab.com/runner/configuration/advanced-configuration/ and https://docs.gitlab.com/runner/executors/docker/); this runner's own version is not recorded (`docs/artifacts/security-review-t811-release-gate-runner-v1.md`), so read `gitlab-runner --version` first and check the same names in that version's documentation. (1) **Services:** in the runner's `[runners.docker]` section add `services_limit = 0` (the maximum number of services per job; the default `-1` means no limit; the tag jobs use none). Optionally also `allowed_services = []`; whether an empty list allows nothing or falls back to "all allowed" is not stated in the documentation **(unverified)**, so `services_limit = 0` is the control. Keep `privileged = false` and do not set `allowed_privileged_services`. Restart the runner and check that the next tag pipeline's three jobs still start. **Check that the option takes effect (SEC-T860-02), in the runner's LXC:** (a) record the version: `gitlab-runner --version`. (b) Before the restart, if `gitlab-runner --help` lists the `lint` command, run `gitlab-runner lint --config /etc/gitlab-runner/config.toml`: per the runner's documentation it reports unknown or misspelled keys, "which the TOML decoder otherwise silently ignores", and exits non-zero on any problem. (c) Restart with `gitlab-runner restart` ("stops and then starts the GitLab Runner service"), then read the runner log: `journalctl -u gitlab-runner --since "-10 min"` (the systemd unit is `gitlab-runner.service`; a runner started with `--syslog` logs to syslog instead). (d) A `lint` failure, or any lint or log line that names `services_limit` as unknown, unsupported, invalid or deprecated, means this version does not take the option: stop, do not rely on it, and report it to the Security Engineer. Because the TOML decoder ignores an unknown key **without** a message, a clean log alone does not prove the option is read: when `lint` is missing, the proof is that `services_limit` is in the `[runners.docker]` table of the documentation for exactly the recorded version (open `gitlab-org/gitlab-runner/docs/configuration/advanced-configuration.md` at the tag `v<version>` of that repository). (e) Record the date, the `gitlab-runner --version` output, the `lint` result (or "no lint command") and the log result in a row of section 5. Sources: GitLab Runner documentation on `main` (`gitlab-org/gitlab-runner/docs/commands/_index.md`, `gitlab-org/gitlab-runner/docs/configuration/advanced-configuration.md`), read through Context7 and https://docs.gitlab.com/runner/commands/ on 2026-11-19; neither states the version that introduced `services_limit` or `lint` **(unverified)**. (2) **Patching:** at every CI image review (`ci_images_reviewed_on`, at most 120 days apart) update Docker Engine and GitLab Runner inside the LXC and the Proxmox VE kernel on the host (then reboot the host), and record the three versions in the image-review row of section 5. The 120 days are the ceiling, not the cadence. **Out-of-cycle trigger (SEC-T860-02):** as soon as a critical advisory for a container escape is published for runc, containerd, Docker Engine, GitLab Runner or the Linux kernel (for example a GitHub Security Advisory of `opencontainers/runc` or `moby/moby`, a GitLab Runner security release, a Proxmox VE kernel security update, or an entry in the CISA Known Exploited Vulnerabilities catalog), patch the affected component at once, without waiting for the next image review, reboot the host for a kernel fix, and record the advisory, the date and the new versions in section 5.
