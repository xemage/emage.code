# MCP pin-bump and release verification checklist

Maintained by the devops-engineer; a Security Engineer reads each bump. Origin: T676 (register items SEC-T646-03, -04, -05, -06, SEC-T655-06, -07, SEC-T658-02, SEC-014, T638-L-2, -8, K-17, K-20, SEC-T675-03, -09; review follow-ups SEC-T676-01 to -10). The `github` MCP container (T638-L-3) is no longer shipped (v9.0.0, user decision 2026-10-22), so it has no section here. Based on: `docs/artifacts/tracked-debt-register-v1.md`, `docs/artifacts/security-review-t675-ci-release-hardening-v1.md`. The short policy stays in `implementation/PREREQUISITES.md` ("Pin-bump policy") and `docs/wiki/mcp-servers.md` ("Pin maintenance"); this page is the procedure behind it. Keep it current: a bump that changes a step edits this page in the same merge request.

Anything marked **(unverified)** was not observed in a live run.

## 1. Every bump of an `npx` pin (`servers.yaml`)

Run from the repository root. `npm`, network access and `python3` with PyYAML are needed.

1. **Read the pins and the registry state.** `python3 scripts/audit-mcp-pins.py list`, then `python3 scripts/audit-mcp-pins.py provenance` (pinned version and `latest`, provenance yes/no).
2. **Provenance preference (SEC-T646-03, T638-L-8).** Pin the newest version that has an npm provenance attestation (`dist.attestations.provenance`). If the newest version has none but an older one has, pin the newer only with a written reason in the merge request. If the package has never published provenance, record the exception and do the extra review below. State on 2026-10-22: provenance present for `@zereight/mcp-gitlab`, `@playwright/mcp`, the three `@modelcontextprotocol/server-*` packages and `@supabase/mcp-server-supabase`; **absent, and absent from every published version, for `@brave/brave-search-mcp-server` and `toolradar-mcp`** (exceptions).
   Extra review for a package without provenance, or with a single maintainer (`@zereight/mcp-gitlab`, `toolradar-mcp`, `@brave/brave-search-mcp-server`): `npm view <pkg>@<new> maintainers scripts.install scripts.postinstall dependencies --json`, `npm diff --diff=<pkg>@<old> --diff=<pkg>@<new>` read for new network, process or file access, and the unpacked size against the previous version (`toolradar-mcp` ships a 750 KB bundle that a diff does not make readable: treat a size jump as a reason to hold the bump). The scripts run with `--ignore-scripts` in the audit, so an install script is read, never executed, by the audit.
3. **Audit (SEC-T646-05, K-17).** `python3 scripts/audit-mcp-pins.py audit --audit-level low`. The audit fails closed (a reply without both `vulnerabilities` and `metadata` is an error; an unknown severity counts as critical) and runs npm with an empty user and global `.npmrc` and `--registry https://registry.npmjs.org/`. It writes a throwaway `package.json` from the pins into a temporary directory, resolves it with `npm install --package-lock-only --ignore-scripts` and runs `npm audit`. Add `--signatures` for a full `--ignore-scripts` install and `npm audit signatures` (registry signatures and provenance of the whole tree). Exit 1 means a finding at or above the level: record it in the merge request with the applicability to stdio use, or do not bump. A finding the user has accepted is passed as `--accept GHSA-xxxx-xxxx-xxxx:YYYY-MM-DD` (repeatable; the expiry date is mandatory; an accepted advisory is still printed as ACCEPTED and an expired acceptance fails the run); every acceptance needs an artifact. The only one today is `docs/artifacts/brave-audit-acceptance-v1.md` (five sdk advisories of the pinned `@brave/brave-search-mcp-server@2.1.4`, expiry 2026-11-21 or the next brave release). `python3 scripts/audit-mcp-pins.py generate DIR` writes the same manifest (and `requirements-uvx.txt`) if you want to run other tools on it.
4. **Manual advisory read for the three reference servers (SEC-T646-06).** `@modelcontextprotocol/server-memory`, `-sequential-thinking` and `-filesystem` moved from calendar versions (`2025.x`, `2026.x`) to `1.0.0` (published 2026-10-11) and to `2.0.0` (2026-10-19). Semver sorts the calendar-form advisory ranges above `1.0.0` and `2.0.0`, so `npm audit` can over- and under-report. For each: open the GitHub Advisory Database (ecosystem npm) for the package, read every advisory's affected range and fix date, and decide whether the pinned version is affected by date and by changed code, not by the sorted range. To list the registry's own advisories for probe versions: `POST https://registry.npmjs.org/-/npm/v1/security/advisories/bulk` with `{"<pkg>": ["0.0.1", "<a calendar version>", "<the pin>"]}`. Record the date and result in section 5.
5. **Edit the pin** in `implementation/knowledge/mcp/servers.yaml` and in `APPROVED_NPX_PINS` of `tests/functional/test_mcp_package_pins.py` together, run `node implementation/scripts/sync.mjs --root implementation` and `python3 implementation/scripts/generate-registry.py`, and declare the projection drift as usual.
6. **Playwright only.** (a) Re-check every flag against `npx -y @playwright/mcp@<new> --help`. (b) **Browser security version (SEC-T655-06):** the browser is patched only at a pin bump. Install it with `npx -y @playwright/mcp@<new> install-browser chrome-for-testing`, read its version (`~/.cache/ms-playwright/chromium-<revision>/.../chrome --version`, or the revision's `browsers.json` entry) and compare it with the current Chrome for Testing Stable (`https://googlechromelabs.github.io/chrome-for-testing/last-known-good-versions.json`, field `channels.Stable.version`). Rule: do not accept a bump whose browser is more than one major behind Stable, and treat a Stable release that fixed an exploited-in-the-wild Chrome vulnerability (Chrome releases blog, CISA KEV) after the bundled version as a blocker for the bump; if no newer `@playwright/mcp` exists, record the delay and decide with the Security Engineer. State on 2026-10-22: bundled Chrome for Testing 155.0.8059.12 (0.0.83), Stable 156.0.8078.47, one major behind, `@playwright/mcp` latest is 0.0.83. Update the browser version in `implementation/PREREQUISITES.md`. (c) **Blocked-origins re-check (SEC-T655-07):** the list is a glob list the package turns into `*://<entry>/**` patterns (`originOrHostGlob` and `globToRegexPattern` in `playwright-core/lib/coreBundle.js`). After any change re-run the matcher on a sample of URLs that must be blocked (metadata names, `168.63.129.16`, `192.0.0.192`, `198.18.0.1`, multicast, NAT64 `[64:ff9b::...]`, 6to4 `[2002:...]`, wildcard-DNS names such as `127.0.0.1.nip.io`) and that must stay allowed (`example.com`, `internal.example.com`, `192.0.2.1`). `tests/functional/test_blocked_origins_matcher.py` holds those samples and a port of the vendor function; set `PLAYWRIGHT_CORE_BUNDLE=<install dir>/node_modules/playwright-core/lib/coreBundle.js` and it also runs the real vendor functions with `node` and requires the same answers (2026-10-22: 39 entries, the port and `playwright-core` of 0.0.83 agree on every sample). The 39-entry list is pinned by `tests/functional/test_mcp_package_pins.py`. Residual gaps, closed only by egress filtering and not by this list: DNS names that resolve to internal addresses and are not in the wildcard-DNS list or are not `*.`-subdomains of it (the apex names `localtest.me` and `lvh.me` ARE listed; the apex of `nip.io` and `sslip.io` does not resolve to a private address), Teredo addresses (`2001:0:...`, whose serialised form varies with zero compression, so no safe glob was added), redirects, WebSockets, a trailing-dot form of `*.internal.` / `*.local.`, IPv4-mapped forms other than `[::ffff:`.
7. Run the gates of the task brief and the full suite.

## 2. Python pins and hash locks (SEC-T646-04, SEC-014, T638-L-2, SEC-T675-09)

- **`uvx` pin** (`mcp-server-git`): `python3 scripts/audit-mcp-pins.py generate /tmp/pins` then `uvx pip-audit -r /tmp/pins/requirements-uvx.txt --no-deps --disable-pip`. PyPI has no npm-style provenance check here; read the release page.
- **Runtime requirement files** (`implementation/runtime/security/requirements-mcp-server.txt`, `implementation/runtime/memory/requirements-mcp-server.txt`): both pin `mcp==2.2.0` and carry the floor `httpx2>=2.12.0` (before 2.12.0: GHSA-8xx6-hgc6-gc2m). Next to each is `requirements-mcp-server.lock.txt`, the hash-locked complete set for Python 3.10 and later. Users who want integrity: `pip install --require-hashes -r implementation/runtime/security/requirements-mcp-server.lock.txt`. The two locks must be byte-identical (a test enforces it). Regenerate after any change of either input, from its own directory:
  `uv pip compile requirements-mcp-server.txt --universal --python-version 3.10 --generate-hashes --exclude-newer <UTC timestamp of the day> -o requirements-mcp-server.lock.txt` (`--exclude-newer` makes the run reproducible; the current locks use 2026-10-22T12:00:00Z and the date is in the file header)
  (`uv` is only needed by the maintainer; `pip-compile --generate-hashes` from pip-tools produces the same kind of file but resolves for one platform, so `uv --universal` is the reference). Then `uvx pip-audit -r <lock> --no-deps --disable-pip`.
- **CI lock files**: `ci/requirements-ci.in` and `ci/requirements-gate.in` are the inputs of the `unit-tests` and `validation-super-gate` jobs; `ci/requirements-ci.txt` and `ci/requirements-gate.txt` are the locks (`uv pip compile ci/requirements-ci.in --universal --python-version 3.12 --generate-hashes --exclude-newer <UTC timestamp> -o ci/requirements-ci.txt`, same for the gate). The jobs run `pip install --require-hashes --only-binary=:all: -r ci/requirements-*.txt` (wheels only: an sdist would run its build backend inside the job; the line is a quoted YAML string because `:all: ` would otherwise parse as a mapping); `tests/functional/test_ci_hash_pins.py` fails on any other `pip install`, on a lock entry without a hash, on an input that is missing from its lock, and on a stale version. `mcp` in the CI lock must equal the pin in `requirements-mcp-server.txt`. After regenerating, install the locks in the real image to prove they resolve on musl (done on 2026-10-22: both locks install, `import yaml, jsonschema, requests, pyarrow, cryptography, mcp` works). With a remote Docker host, bind mounts do not work: stream the directory, `tar c ci | docker run --rm -i python:3.12-alpine@sha256:<pinned digest> sh -c 'mkdir /w && tar x -C /w && cd /w && python3 -m pip install --no-cache-dir --require-hashes --only-binary=:all: -r ci/requirements-ci.txt'` (2026-10-22: both locks install wheels-only in the pinned image; a changed version fails with a hash mismatch).

## 3. CI images and the pipeline (SEC-T675-03)

Only two bases remain: `node:24-alpine` (default image) and `python:3.12-alpine`. To bump one: read the index digest from the Docker Hub registry API (`https://auth.docker.io/token?service=registry.docker.io&scope=repository:library/<name>:pull`, then `GET /v2/library/<name>/manifests/<tag>`), confirm the body hashes to the digest, run the image to read its Alpine and runtime versions, re-read the `apk add` package versions of that Alpine branch, and change digest and `~=` pins together in `.gitlab-ci.yml`. End-of-life tags fail `tests/functional/test_ci_hash_pins.py` (Node 20 and below or an odd major, Alpine 3.21 and below, Python 3.9 and below, as of 2026-10-22: update the table when a line goes end of life). Digests used by T676: `node:24-alpine` `sha256:06d7adf3...` read 2026-10-22 (Alpine 3.24.3, Node 24.22.1). `python:3.12-alpine` `sha256:92abd2ba...` re-read 2026-10-22 (Alpine 3.24.3, Python 3.12.15; replaces the 2026-10-16 digest in every job). The pipeline carries `# ci_images_reviewed_on: <date>` and `test_ci_hash_pins` fails when it is older than 120 days or older than the end-of-life table: re-read the digests, re-check the table, update both dates. The commands of the jobs were run once in these images on 2026-10-22 (`verify.mjs`, `sync.mjs` plus `git diff`, the markdown link check, the super gate with the locked packages, `verify-release-docs.py`); the first real pipeline is still the proof **(unverified until it runs)**.

## 4. Release verification

Before the release merge request, in addition to the gates of the task brief:

- [ ] `python3 scripts/audit-mcp-pins.py audit --audit-level high --signatures --accept GHSA-6qxp-vccf-f47h:2026-11-21 --accept GHSA-22jm-h49p-29qw:2026-11-21 --accept GHSA-6prh-2h8m-c8cw:2026-11-21 --accept GHSA-46jr-4wx8-v453:2026-11-21 --accept GHSA-rvq5-wwqv-78pq:2026-11-21` (exactly the five advisories of `docs/artifacts/brave-audit-acceptance-v1.md`, nothing broader) and `provenance`: no other finding; findings recorded or fixed. After 2026-11-21 or the first brave release above 2.1.4 the acceptances expire and the command must pass without them.
- [ ] Section 1 steps 4 and 6 done for every pin bumped since the last release (the three reference servers are always re-read at a release).
- [ ] CI image digests re-read (section 3), the Python locks regenerated if an input changed.
- [ ] `python3 scripts/check-gitlab-token.py` with the token the MCP server will use (user step).
- [ ] The one-time live checks of section 6 recorded for the release client versions.

## 6. One-time live checks of the denials (SEC-T658-02, K-20)

The Gemini and Opencode denials of the six Playwright tools (`browser_run_code_unsafe`, `browser_evaluate`, `browser_file_upload`, `browser_drag`, `browser_drop`, `browser_network_request`) were written from vendor documentation and source. A name-format mismatch would deny nothing and fail silently (open). Do these once before the next release, again after any change of `denyTools` or of the client major version, and write the date, client version and result in the table.

**Opencode** (partly observed on 2026-10-22, opencode 1.18.31):
1. In a throwaway directory with an empty home: copy `.opencode/opencode.json` and `.opencode/agents/` from the generated tree, then run `t=$(mktemp -d); env -i PATH="$PATH" HOME="$t" XDG_CONFIG_HOME="$t/.config" XDG_DATA_HOME="$t/.local/share" XDG_CACHE_HOME="$t/.cache" XDG_STATE_HOME="$t/.local/state" opencode debug config > "$t/config.json"` and read only the denies, for example `grep -o '"playwright_[a-z_]*": "[a-z]*"' "$t/config.json"`: expect the six `playwright_<tool>: deny` keys. Set `t` in the calling shell BEFORE `env -i`, and quote it: a `$HOME` inside the `env -i` words expands in your own shell and points the tool at your real configuration. **Never run `opencode debug config` with your real home, and never print the file: it contains your global configuration, including any header or key in it.**
2. `opencode agent list` (same `env -i ... HOME="$t" ...` words and the same `t`, output redirected to a file in `$t`) prints each agent's resolved rules. For the last matching rule of `playwright_browser_evaluate` expect `deny` in every agent, and for a generated agent that holds no GitLab merge tool `gitlab_merge_merge_request` expect `deny`. Observed 2026-10-22 on 35 agents (the built-in `build`, `plan`, `general` allow the GitLab and GitHub tools, which is the documented gap).
3. Still to do **(unverified)**: in a real session, ask the model to call `playwright_browser_evaluate`; expect a refusal before the browser runs.

**Gemini CLI** (not run **(unverified)**; the CLI is not installed on the T676 host):
1. Put the generated `.gemini/settings.json` in a project, start `gemini`, run `/mcp`, and check that `playwright` lists tools but **none** of the six (the `mcp_playwright_<tool>` form).
2. Ask the model to call `mcp_playwright_browser_evaluate`; expect "tool not found" or a refusal.
3. If a tool of the six is listed, `excludeTools` did not match the reported name: stop the release and open a finding.

**Other items of K-20, observation only** **(unverified)**: GitHub Copilot per-agent MCP grants (do the `qa-engineer` and `frontend-developer` agents get the Playwright tools, and the others not?), Pi's handling of the agent tool list, the `--sandbox` flag of the `playwright` entry on a host with unprivileged user namespaces disabled (expect a start failure; record the message).
