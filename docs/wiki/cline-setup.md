# Cline Setup

How to install and use emage.code with [Cline](https://cline.bot).

## Install steps

```bash
git clone https://gitlab.com/em-age/emage.code.git
cd emage.code
scripts/install.sh --target /path/to/your-project --platform cline
```

This installs, into your target project root:

- `.clinerules/` — project rules as `.md` files with `paths` frontmatter, directly
  usable by Cline (no manual copy step needed).
- `.cline/skills/` — skill definitions, directly usable by Cline.
- `.cline/mcp.json` — an MCP server **staging file**. This file is generated for
  convenience but is **not automatically applied** by Cline — Cline reads MCP
  server configuration from its own global config, not from a project-local
  file. See [MCP server setup](#mcp-server-setup-copying-clinemcpjson-into-clines-global-config)
  below for how to bring these servers into Cline.

Also plain `AGENTS.md` at your project root — Cline auto-detects this file
natively for cross-tool compatibility (confirmed during the platform
integration work for this release), so no additional projection step is
required to get workspace conventions loaded.

**Scope note — subagents and slash commands are not included in this release.**
emage.code ships 27 specialist subagents and 18 slash commands to other
platforms (Claude Code, Cursor, etc.), but **Cline support in this release
covers only rules, skills, and the MCP staging file**. As of this writing, no
confirmed on-disk format for Cline-native subagents (`.cline/agents/`) or
slash commands exists in Cline's documentation, and emage.code does not invent
one. This is an intentional, documented scope boundary, not an oversight — it
will be revisited in a follow-up release if Cline documents a subagent/command
format.

## Plan/Act mode best practices for emage.code workflows

Cline's Plan/Act mode maps naturally onto this repo's **Plan → Approve →
Execute** lifecycle (see `AGENTS.md` § Delegation Brief):

- **Plan mode** — use this for everything the orchestrator would normally do
  before implementation: reading the task ledger (`docs/tasks/active-tasks.md`),
  drafting or reviewing a delegation brief, and proposing an approach. Treat
  Cline's plan output as the human-approval checkpoint the workflow requires —
  don't switch to Act mode until the plan reflects the agreed scope,
  constraints, and acceptance criteria.
- **Act mode** — use this for the actual implementation once a plan is
  approved, mirroring the "Execute" step. Keep changes scoped to what the plan
  described; if Act mode surfaces a need to go beyond the approved plan (a new
  file, a schema change, a different library), switch back to Plan mode rather
  than silently expanding scope — the same discipline the workflow expects
  from any agent.
- Because emage.code's task ledger and checkpoints are files under version
  control (`docs/tasks/`, `docs/checkpoints/`), Cline can read and update them
  directly in either mode — there is no special integration required beyond
  normal file access.

## MCP server setup (copying .cline/mcp.json into Cline's global config)

Cline's MCP configuration is **global**, not per-project: the CLI reads from
`~/.cline/mcp.json`, and the IDE extension manages the same configuration
through its own settings panel (MCP Servers icon → Configure → "Configure MCP
Servers"). Always check Cline's current documentation for the exact path/UI,
since this detail can change between Cline releases.

Because the config is global, `.cline/mcp.json` generated by
`scripts/install.sh` is a **staging file** — copy its contents into your real
Cline config, and **merge, don't overwrite**, since you may already have other
MCP servers configured there.

Example merge — your existing global config has one server already:

```json
{
  "mcpServers": {
    "my-existing-server": {
      "command": "npx",
      "args": ["-y", "my-existing-server"]
    }
  }
}
```

After merging in the `gitlab` entry from the generated `.cline/mcp.json`:

```json
{
  "mcpServers": {
    "my-existing-server": {
      "command": "npx",
      "args": ["-y", "my-existing-server"]
    },
    "gitlab": {
      "command": "npx",
      "args": ["-y", "@zereight/mcp-gitlab"],
      "env": {
        "GITLAB_PERSONAL_ACCESS_TOKEN": "${env:GITLAB_PERSONAL_ACCESS_TOKEN}",
        "GITLAB_API_URL": "${env:GITLAB_API_URL}"
      }
    }
  }
}
```

Set the referenced environment variables (`GITLAB_PERSONAL_ACCESS_TOKEN`,
`BRAVE_API_KEY`, …) before starting Cline — see [MCP Servers](mcp-servers) for
the full env-var contract. Never commit real values for these variables.

## Troubleshooting: rules not loading

If `.clinerules/` content doesn't appear in Cline:

- **Check the location.** `.clinerules/` must exist directly at your project
  root — not nested inside a subdirectory, and not renamed. If you used
  `scripts/install.sh --platform cline`, confirm it targeted the correct
  `--target` directory.
- **Check your Cline version.** Project-level rules support has been present
  in recent Cline releases; if rules aren't showing up in the Rules panel,
  check you're on a recent Cline version and update if needed — check Cline's
  current docs/changelog for the specific version that introduced this if you
  need to confirm.
- **Check file extensions.** Only `.md` and `.txt` files inside `.clinerules/`
  are read; confirm the generated rule files weren't renamed or stripped of
  their extension during a manual copy.
- **Check frontmatter.** Rule files use a `paths` key (glob array) in
  frontmatter for path-scoped rules. A malformed YAML frontmatter block can
  cause Cline to skip a rule file — validate the frontmatter is well-formed
  YAML if a specific rule isn't applying.
