## Context

T775 found that Gemini CLI v0.67.0 enforces per-subagent tool lists while this harness drops them (`gemini.json` `"tools": "drop"`), that the 28 generated Gemini agent files probably fail Gemini's strict loader, and that the SEC-T657-01/SEC-T658-01 remainder stays MEDIUM. The user chose removal over the fix. This ADR settles how, in the steps of ADR-013. Gemini differs from Pi in five ways that need their own decisions: no emitter is shared, so no refactor commit is needed (inv. G5, § 3); the generator writes a Gemini-only hook (G5); `merge-mcp-json.py` has two Gemini-only merge rules (G12); `.gemini/settings.json` is Gemini CLI's general project settings file and `.gemini/` is also Gemini CLI's own folder, holding for example `.env` (G21 a, f); and the Pi removal made Gemini the second host platform of several installer tests (G16).

Since the inventory, T774 (`f43e2dee`, root refresh of the Pi removal) has merged. Line numbers of root files cited from the inventory (root `AGENTS.md`, the drift baseline) may have shifted; S1 re-reads them.

## Decision drivers

1. Completeness, with a **closed** list of intentional residue (lesson of TL-T773-01: every grep hit is either removed or listed).
2. No other platform's generated bytes change, Opencode's `permission` and per-agent denials included (plan-146 Risks, row 3; inv. § 3).
3. No adopter data loss. Stronger than for Pi: `.gemini/` is certainly Gemini CLI's own folder and `.gemini/settings.json` may hold the user's own Gemini settings (G21 a, f).
4. Delete code whose only user was Gemini; keep code that another platform reads (`denyTools`, G6).
5. The project's rules: SemVer with a migration guide, immutable history, no golden edit without a grant, root refresh only with the user's approval, user-owned files untouched.

### D4. Adopter behaviour

Today `--update`/`--projections-only` sweeps `$TARGET/.gemini/` with `rsync -a --delete`, excluding only `settings.json` and its sidecar, so **the user's own Gemini CLI files there are deleted** (G10, G21 f). After a plain removal `.gemini/` is never touched, and `--platform gemini` fails as an unknown platform before any write (inv. § 4).

| Option | Verdict |
|---|---|
| A. Unknown-platform error only | Rejected: silent freeze of the GitLab entry, pins and Playwright hardening in `.gemini/settings.json` |
| **B. Removal message plus read-only notice, never delete (ADR-013 D5)** | **Recommended** |
| C. Delete generator-owned files on `--update` | Rejected: writes inside Gemini CLI's own folder and into the user's general settings file; needs a new prune path |

Specification (behaviour, not code), as ADR-013 D5 with these Gemini differences:

1. **Removal message** in the early validation (`install.sh` 184-201, before any write), a case matching `gemini` in every letter case next to `cursor` and `pi`: `error: platform 'gemini' was removed in v11.0.0 (see docs/releases/v11.0.0.md). Existing .gemini/ files in your project are not touched. Nothing was written.` Exit 1, in plain install, `--update`, `--projections-only` and `--dry-run`. The usage list loses `gemini`; `--platform all` creates no `.gemini`.
2. **Notice** from `validate_before_update`, if `$TARGET/.gemini` is a directory and not a symlink, and either `$TARGET/.gemini/.generated-manifest.json` (a regular, non-symlink file) contains `"platform": "gemini"` or `$TARGET/.gemini/settings.json.provenance.json` exists (G11). One stderr block, exit 0. **It reads nothing else**: never `.gemini/settings.json` content and never `.gemini/.env` (G11, G21 f). Content: Gemini CLI is no longer supported; `.gemini/` is no longer updated, pruned or checked; the MCP server pins, the Playwright hardening and the GitLab entry in `.gemini/settings.json`, and the harness's post-edit hook there, are frozen at the version that wrote them; **`.gemini/settings.json` may also hold your own Gemini settings, so cleanup means removing the harness's entries, not deleting the file or the folder**; see the migration item. Installs older than both markers are not detected (first release that wrote them: **(unverified)**, G11).
3. **Never delete**, in any mode.
4. Implementation latitude as ADR-013 D5.4: a third function or one table-driven function over the removed platforms, Cursor and Pi behaviour and tests unchanged, 50-line limit.
5. **Tests** (in `test_install_removed_platform_v11.py`, as ADR-013 D5.5 and inv. § 6.4): `--platform gemini` in all four modes and letter cases (exit 1, message, nothing written, target not created); help text; `--platform all` creates no `.gemini`; a v10.0.0-tag install (`git archive v10.0.0`, the CI fetch already exists, ADR-013 deviation b) with a user file in `.gemini/`, an edited `settings.json` and a `.gemini/.env` holding a dummy value: `--update` and `--projections-only` exit 0, print the notice, leave every byte under `.gemini/` unchanged; each marker alone; no notice without markers, for a symlinked `.gemini` or a symlinked marker; rsync and cp fallback; a source scan that no write or delete path names `.gemini`; a source scan that the notice names neither `.env` nor a read of `settings.json`.

Pointer check: the message cites `docs/releases/v11.0.0.md`, the same document the Pi message cites. The narrowed skip of `test_verify_release_docs.py` (SEC-T773-01) already covers that one pointer; no further narrowing is needed, and SEC-T773-01's planned tightening ("at most one skipped pointer, the next release") stays compatible. S1 confirms the test passes unchanged **(unverified)**.

**Migration Guide item M-n. Gemini CLI is no longer supported.**

- `--update` and `--projections-only` no longer touch `.gemini/` (before, they replaced it and deleted files you had added there, Gemini CLI's own included). The installer prints a note while it finds a harness-written `.gemini/`.

To clean up: delete the paths listed under `files` in `.gemini/.generated-manifest.json` except `settings.json`. In `.gemini/settings.json`, remove the servers listed under `generatorOwnedKeys` in `.gemini/settings.json.provenance.json` (keep any you want as your own) and the harness's post-edit hook under `hooks.AfterTool`; keep every other key. Then delete the sidecar and the manifest.
- If you keep the harness entries: they are frozen. MCP server pins, the Playwright hardening and the GitLab entry receive no updates; Gemini CLI agents and your main session can call every tool of every configured server except the six denied Playwright tools.
- Automation that runs `--platform gemini` now fails with exit 1; automation that runs `--platform all` and reads `.gemini/` must change.
- Rollback: the v10.x installer with `--update` recreates the harness files and, as before, sweeps `.gemini/` and deletes your own files there.
