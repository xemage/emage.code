## Context

### What is decided and what is open

The user decided to remove Pi support completely. ADR-010 removed Cursor in v9.0.0 with the same steps, and its decisions have been in force since (adopter notice, orphan-tree guard, deletion of both trees). This ADR settles what is different for Pi: Pi shares the MCP emit function with `vscode` (inv. P6), it is the only user of two generic generator features, `skipFormats` and `optional` (inv. P7, P8), it is the only caller of `merge-mcp-json.py --drop-env-form` (inv. P14), and since ADR-010 it is the example platform in many installer tests (inv. § 11.3). It also settles the version, the adopter behaviour, the tracked trees, the registry and schemas, the security consequences and the task order.

## Decision drivers

1. Completeness: no manifest, tree, flag, branch, enum or live doc claim left, with a short list of what stays as history.
2. No other platform's generated bytes change (plan-146 Risks, row 3).
3. No adopter data loss: the installer never deletes anything under `.pi/`. This matters more than for Cursor, because `.pi/` may also be Pi's own project folder (inv. § 4, last row, **(unverified)**).
4. Keep generic code that still has a non-Pi reader; delete code whose only user was Pi.
5. Keep the generic SEC-T680 merge-script guards and their tests (inv. P14, § 6.2).
6. The project's rules: SemVer with a migration guide, immutable history, no golden edit without a grant, root refresh only with the user's approval.

### D5. Adopter behaviour

Today `--update`/`--projections-only` replaces `$TARGET/.pi/` with `rsync -a --delete` (excluding `mcp.json` and its sidecar), so user files inside `.pi/` are deleted; after a plain removal `.pi/` is never touched again, and `--platform pi` fails as an unknown platform before any write (inv. § 4, adopter table).

| Option | Behaviour | Verdict |
|---|---|---|
| A. Unknown-platform error only | Silent freeze of `.pi/mcp.json` and agent tool lists | Rejected: no signal of the frozen security state |
| **B. Removal message plus read-only notice, never delete (ADR-010 D3 B)** | See below | **Recommended** |
| C. Delete generator-owned files on `--update` | Deletes inside a folder that may be Pi's own project folder (inv. § 4, **(unverified)**) and needs a new prune path | Rejected |

Specification (behaviour, not code):

1. **Removal message.** In the early validation (`install.sh` 183-197, before any write), the value `pi` gets its own case next to `cursor` (186-190): `error: platform 'pi' was removed in v11.0.0 (see docs/releases/v11.0.0.md). Existing .pi/ files in your project are not touched. Nothing was written.` Exit 1. Applies to plain install, `--update`, `--projections-only` and `--dry-run`. The supported list in the usage text loses `pi`.
2. **Notice.** In `validate_before_update` (runs for `--update` and `--projections-only`), if `$TARGET/.pi` is a directory and either `$TARGET/.pi/.generated-manifest.json` contains `"platform": "pi"` or `$TARGET/.pi/mcp.json.provenance.json` exists (F7), print one stderr block and continue with exit 0. Content: Pi is no longer supported; `.pi/` is no longer updated, pruned or checked; the MCP server pins, Playwright hardening and GitLab tool grants in `.pi/mcp.json` and `.pi/agents/*.md` are frozen at the version that wrote them; the installer does not delete them; see the migration item. Reads only (`-d`, `grep -q`, `-e`); writes nothing. Installs older than the manifest and the sidecar are not detected (which release first wrote them is **(unverified)**, inv. § 4).
3. **Never delete**, in any mode. `--platform all` no longer includes Pi.
4. Implementation latitude: the Cursor notice (`install.sh` 1276-1302) and the new Pi notice may be one table-driven function over the removed platforms, provided the Cursor behaviour and its tests stay unchanged and the 50-line function limit holds.
5. **Tests** (as ADR-010 D3.4): (a) `--platform pi` in all four modes: exit 1, message, target directory not created, nothing changed; (b) a pre-removal target built from the `v10.0.0` tag with `.pi/` plus a user-added file and an edited `.pi/mcp.json`: `--update` and `--projections-only` exit 0, print the notice, leave every byte under `.pi/` unchanged; (c) no `.pi/`: no notice; (d) `.pi` a symlink: no write through it, exit 0; (e) rsync and cp-fallback copiers for (b).

## Consequences

- **Positive**: one manifest, two 91-file trees, one emit branch, one tool-name style, two generator features' Pi paths and one merge-script flag fewer; the SEC-T657-01/SEC-T658-01 remainder shrinks to Gemini CLI; `--update` stops sweeping a folder that may belong to Pi itself.
- **Negative**: a MAJOR release; Pi users lose updates and clean up by hand; about 30 test files and a docs sweep change; ADR-010 and three immutable artifacts keep Pi statements that readers must interpret with this ADR.
- **Risks introduced**: frozen adopter `.pi/` state (D11); a byte change in vscode output if the D2 proof is skipped; a re-pointed fixture platform lacking the property the test relied on (D8).
- **Follow-ups**: release-manager writes the Breaking-changes entry and migration item from Appendix A in the v11.0.0 plan; register v12 marks the Pi parts of K-15, K-20/A-7 and SEC-T680-02..04 as ended or moot; T775 (Part C) starts after T774.

- `--update` and `--projections-only` no longer touch `.pi/` (before, they replaced it and deleted files you had added there). The installer prints a note while it finds a harness-generated `.pi/`.

- Automation that runs `--platform pi` now fails with exit 1; automation that runs `--platform all` and reads `.pi/` must change.
- Rollback: the v10.x installer with `--update` recreates `.pi/` and, as before, replaces it wholesale.
