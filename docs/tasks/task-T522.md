## Objective

Collect the promotion that `T520`'s merge and `T518`/`T520`'s archival made available. Flip
`agent/security-engineer` and `command/security-audit` from `maturity: experimental` to
`maturity: stable`, regenerate the derived registry, and update the one distribution snapshot
test that records how the 79 components are spread across tiers.

`command/security-audit` becomes **the repository's first `stable` command**. `plan-064`'s
Phase 9 baseline was `0 of 19` commands `stable`; this is `1 of 19`.

## Why this is its own task

`T520` executed `ADR-007`'s verdicts and deliberately promoted nothing — a component-state change
is separate work from the defect fix that unblocks it, and `T514` set that precedent. `T520` was
also `P1` and declared `**Affects:** command/security-audit`, so that component stayed
ledger-blocked by criterion 3 until the row archived. Promotion was therefore not merely undesirable
inside `T520`, it was **impossible**: the criteria could not have been met while the task performing
it was open.

`P2` is deliberate and carries the same reasoning as `T514`: a `P0`/`P1` row declaring these
components would re-enter criterion 3/7's open-defect scan and block the very promotion this task
exists to perform. The work also genuinely is nice-to-have — it banks value already earned by
`T516`, `T518` and `T520` and blocks nothing downstream.

## Conflict of interest — disclosed, not assumed away

This task was measured and executed by the **same** actor (the top-level orchestrator session).
`T514`'s closure controlled the equivalent risk by having a second party re-verify. That control is
not available here, so it is replaced by a weaker but real one: **the gate is mechanical and
reproducible in one command**, and the reviewer is asked to run it rather than trust this brief.

```
python3 implementation/scripts/check-maturity.py --root implementation
```

Expected: `79 components checked, 0 failing their claimed level.`, with `agent/stable: 26` and
`command/stable: 1`. If that command disagrees with this brief, this brief is wrong.

## Two steps the "two one-line flips" framing missed

Both were found by running the suite, not by reading the diff:

1. **`implementation/registry/` is generated and carries `maturity:`.** `sync.mjs` does *not*
   propagate it — the platform projections (`.claude/`, `.gemini/`, …) carry no `maturity:` field at
   all, so `implementation/scripts/sync.mjs --check` reports `no drift across 577 files` and gives
   no signal whatsoever. `generate-registry.py` must be run separately, or the registry drift gate
   fails (`test_validation_gate.py::test_registry_gate_passes_for_repo_artifact`).
2. **`test_check_maturity.py` hardcodes the tier distribution** and fails on any legitimate
   promotion.

## On editing a test in a promotion task

`T514` §4.1 already established this and the same reasoning applies unchanged:

- The edit converts **no** maturity `FAIL` into a `PASS`. `orchestrator` and `tech-lead` still fail
  and are still `experimental`; no component's outcome changed because of it.
- The **load-bearing** assertions in that test — `returncode == 0` and
  `79 components checked, 0 failing` — are untouched. Those are the gate.
- The edit is strictly **additive in strength**: a new `command/stable: 1 pass, 0 fail` assertion
  is added, locking in the first stable command so a silent regression to `0` would now fail.

The method name still reads `..._at_experimental_baseline`, which has been inaccurate since `T514`.
It was **deliberately not renamed**: `docs/tasks/completed-tasks.md` (T495 row) and
`docs/artifacts/agent-promotion-rerun-v1.md` §4.1 both cite it by name, and a rename would break two
citations to buy a cosmetic fix.
