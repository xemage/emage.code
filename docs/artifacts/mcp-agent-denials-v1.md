## 1. Result

The generator now writes per-agent `false` entries into every Opencode agent file (`implementation/.opencode/agents/*.md`, `tools:` map):

1. For every agent: `playwright_<tool>: false` for each `denyTools` entry of the `playwright` server (the six excluded tools), last in the map.
2. For every non-exempt server of `servers.yaml` (11 of the 17 that the Opencode manifest carries; every entry declares `denyUnlessGranted`, `true` or an explicit `false` exemption, section 3a): `<server>_*: false` in every agent file whose source tool list holds no token of that server, written after the allows.
3. For an agent that holds only **named** tools of a server (for example qa-engineer and scrum-master for `gitlab`): `<server>_*: false` in the leading block of the map, before every allow, so that its named `<server>_<tool>: true` entries after it are the only tools of that server it can call (section 4a). An agent that holds the whole server (`mcp__<server>`) gets no deny for it.
4. The generator refuses to run if an agent would hold an allow and a deny of the same name.

Status: the mechanism rests on the vendor **source and on the resolver output** of `opencode-ai@1.19.2` (`opencode debug agent`, raw output stored in `mcp-agent-denials-evidence-v1.md`); the vendor documentation marks the `tools` map deprecated and does not state that its key order is the rule order (section 2, row 1). **No refused tool call was observed.** The unverified items are listed in section 7; they are shipped as documented limits, not as verified behaviour.

### 2.1 What the evaluation means for the generated files

- **Per-agent `false` beats the global config in both runtimes.** A user's global `permission` with `gitlab_*: allow` or `*: allow` does not re-enable GitLab for a non-holder, and does not re-enable one of the six Playwright tools for any agent. Tests model the order independently (`tests/functional/test_mcp_agent_denials.py`, `OpencodeEvaluationTests`).
- **Deny last.** `playwright_*: true` followed by `playwright_browser_evaluate: false` denies the tool; the reverse order allows it. So the generator writes the denies after every allow (a test pins it for all 28 files), with one deliberate exception: the `gitlab_*: false` of an agent that holds only named GitLab tools comes first (section 4a), so that its named allows win. The one agent shape that holds a wildcard allow and a deny of a name it covers is a whole-server Playwright holder; none ships, and the generator output for it is `playwright_*: true` then the six `false` entries.
- **A user-owned agent file, another config source, a plugin or a managed policy that comes later still wins.** Not changed and not preventable from the generated files. `packages/core/src/permission.ts:173-190` runs a plugin hook `permission.evaluate` that can alter the effect, and `packages/core/src/managed-policy.ts` exists; neither was read in depth **(unverified)**.

## 3. Why a wildcard for GitLab, not a list of write tools

The pinned `@zereight/mcp-gitlab@2.2.5` registers 275 tools (`build/tools/registry.js`, read from the tarball in a scratch directory). The vendor's `readOnlyTools` set holds 145 names; about 130 registered tools are outside it. An exact "write tools" list was rejected because:

- **It fails open.** `execute_graphql` and `gitlab_api_request` are inside `readOnlyTools` yet declared mixed-access (`MIXED_ACCESS_TOOLS`) because they can write; a list derived as "not in readOnlyTools" would miss exactly the two most powerful tools.
- **It goes stale silently.** Every pin bump can add tools; the list would need a registry diff at each bump, with no test able to notice a missed tool.
- **It is not what the roles need.** A non-holder holds no GitLab tool at all (on Claude Code and Copilot it cannot call one); `gitlab_*: false` gives Opencode the same result with one entry per agent file instead of about 130.

Consequence: a non-holder can no longer call GitLab **read** tools on Opencode either (it could before). That equals the other platforms' behaviour and the roles' tool lists.

One caveat of the wildcard, same as the existing `gitlab_*: true`: it also matches a user server whose cleaned name starts with `gitlab_` (for example `gitlab_ee`). A server named `gitlab-ee` or `mygitlab` is not matched (tested).

## 3a. Scope: every non-exempt server (SEC-T663-01) and the user's exemption

The first commits applied `denyUnlessGranted` to `gitlab` only. The review (SEC-T663-01) found that every other server stayed callable by every agent on Opencode. `denyUnlessGranted` is therefore declared on **every** `servers.yaml` entry, and the sync reader rejects an unknown key, so a missing or misspelled flag cannot pass silently. A test requires the flag on every entry; `false` is an explicit, tested choice with a one-line comment in `servers.yaml`.

**User decision, 2026-10-16** (AskUserQuestion; option label verbatim): "Exempt the read/search servers (Recommended)". The per-agent deny does NOT apply to `brave`, `context7`, `hindsight`, `cwso`, `hf-mcp-server` and `toolradar` (`denyUnlessGranted: false`), so generated agents, including an orchestrator selected as the primary agent, keep search, documentation and memory-layer access. The deny (`denyUnlessGranted: true`) stays for the write-capable and project-reaching servers: gitlab, playwright (with its six exact denies), memory, sequential-thinking, security-audit, poc-security-audit, context-retriever, filesystem, github, git, supabase.

Holders are derived from the agent sources by the generator and pinned independently in `tests/functional/test_mcp_agent_denials.py` (`EXPECTED_HOLDERS`): gitlab (whole: 5, named: qa-engineer, scrum-master), playwright (named: qa-engineer, frontend-developer, poc-qa-engineer, demo-agent), memory (whole: orchestrator, poc-orchestrator), sequential-thinking (whole: orchestrator, poc-orchestrator, solution-architect), security-audit (named: security-engineer, poc-security-engineer), poc-security-audit (named: poc-security-engineer), context-retriever (named: context-retriever).

Consequence, intended and stated: a non-exempt server that **no** agent lists (`filesystem`, `github`, `git`, `supabase`) is denied in every generated Opencode agent file. Comparison with the other platforms: on Claude Code a subagent whose `tools` allowlist lacks the server's tokens cannot call its tools, so for subagents the result is the same; the difference is the main session, which is not a subagent on Claude Code and keeps every configured server, whereas an Opencode agent file such as the orchestrator can be the primary agent and is denied the non-exempt servers it does not hold. The exempt servers (including `hindsight`, which `AGENTS.md` describes as available to the session) are not affected. The way to reach `filesystem`, `github`, `git` or `supabase` from Opencode: a built-in agent (build, plan, ...) or an agent file of your own (neither gets a per-agent deny, section 7), or add the server's `mcp__<server>` token to an agent's source and regenerate. The key order and the same-name guard hold for all servers (tested for every non-exempt server and agent). Name checks: the cleaned names are distinct and no wildcard of one server matches a name of another (for example `git_*` does not match `github_x`, `security-audit_*` does not match `poc-security-audit_x`).

## 4. What is emitted, and from where

Single sources: `denyTools` on the `playwright` entry (T658) and `denyUnlessGranted` (`true`, or the explicit exemption `false`) on every entry of `implementation/knowledge/mcp/servers.yaml` (an unknown key in a server entry, such as a misspelled `denyUnlessGrant`, stops `sync.mjs`); the new manifest key `frontmatter.agents.mcpAgentDenies: true` in `implementation/platforms/opencode.json` (the only platform that sets it; it requires `mcpToolNames: "underscore"` and `tools: "object"`, validated at manifest load). `implementation/scripts/sync.mjs` (`agentMcpDenials`) computes, per agent: the `denyTools` of every server the platform carries (exact names, in `servers.yaml` order), plus `<server>_*` for every server with `denyUnlessGranted` for which the agent's source tool list has no `mcp__<server>` / `mcp__<server>__<tool>` token. `validateDenyTools` rejects a `denyUnlessGranted` that is not a boolean. If a rendered allow equals a deny the run stops with "An agent tool list both grants and denies <name>".

## 4a. Named-subset rule (every server, for example qa-engineer and scrum-master for gitlab)

This is the named-subset rule, added on the orchestrator's decision of 2026-10-16. An agent whose source tool list holds `mcp__<server>__<tool>` tokens and no bare `mcp__<server>` (a server with `denyUnlessGranted`) gets `<server>_*: false` as the first entry of its `tools` map. The generator (`agentMcpDenials` in `sync.mjs`) returns `first` and `last` lists: `first` for named holders, `last` for non-holders and the exact `denyTools`; a whole-server holder gets neither. A bare token together with named tokens counts as a whole-server holder (tested).

- **Why it is safe**: the wildcard and the named entries are different keys, so the "no name both allowed and denied" invariant holds. What makes the pair work is order: Opencode applies the last matching rule, so the later `gitlab_get_issue: true` beats the earlier `gitlab_*: false` for that tool, and every other GitLab tool matches only the wildcard. A wildcard deny moved after the allows would deny the named tools too; a test pins, for every server and every named holder, that every named allow comes after the wildcard deny, and that the leading block holds exactly the wildcards of the servers the agent holds named tools of.
- **Probe result** (`opencode-ai@1.19.2`, `opencode debug agent "QA Engineer"` and `"Scrum Master"`, generated files copied unchanged into a scratch project, plus a hostile user-global `permission` `gitlab_*: allow` as the first user rule). Resolved rule order for QA Engineer (70 rules): defaults, global `gitlab_*` allow (rule 12), the six global Playwright denies (13-18), the agent's own rules: `gitlab_*` deny (19), `read`/`search`/`edit`/`execute`/`web`, the named Playwright allows, the 20 named `gitlab_*` allows (43-62, from `gitlab_create_issue` to `gitlab_discover_tools`), then the six Playwright denies (64-69). Scrum Master (55 rules): the same shape with `gitlab_*` deny at 19, its 24 named allows at 24-47, the six denies at 49-54. Evaluated with last-match-wins over the resolved list: `gitlab_get_issue` and `gitlab_create_issue` allow; `gitlab_merge_merge_request`, `gitlab_push_files`, `gitlab_gitlab_api_request`, `gitlab_execute_graphql` deny for both agents, also with the hostile global allow in place. The evaluation step is my own re-implementation over the resolved rules; no tool call was made.
- **Install**: unchanged; the two files are replaced wholesale like all agent files, so the order is restored on every update.

## 5. SEC-T657-04 (the generated `x: true` entries override a user's own `ask`/`deny`)

The same mechanism confirms the finding and shows the only fix that does not break usage: an agent-level `true` is later than the user's global config and wins (tested: a global `deny` of `playwright_browser_click` is overridden for qa-engineer). It is **not removed**, for two reasons: the entries are the agents' documented grants, and without a matching rule the current core falls back to `ask` (`packages/core/src/permission.ts:87-94`; no default `*` allow was found in `packages/core/src/plugin/agent.ts`, whose `*` rules are denies), so removing them would turn every granted MCP call into a prompt on that line. What changed: allows are emitted only for tools an agent holds (already true since T657), and a tool an agent does not hold keeps the user's own rule (tested: a global `deny` of `playwright_browser_click` still denies it for tech-lead). The override for held tools is **documented** (wiki, `PREREQUISITES.md`, `AGENTS.md`). Status: documented residual, no longer tracked as a defect. Example now stated in both `AGENTS.md` files: a user's own global `ask` (or `deny`) on `gitlab_merge_merge_request` is silently overridden for the five whole-server GitLab holders. Whether a supported way to keep a prompt exists was checked on `opencode-ai@1.19.2` (`mcp-agent-denials-evidence-v1.md`, SEC-T663-03): a global rule and a project `agent.<name>.permission` entry both resolve before the agent's `gitlab_*` allow and lose; only `OPENCODE_CONFIG_CONTENT` (loaded after the agent files) keeps the `ask`, and by source reading (`config/config.ts`) the managed configuration. No supported user-level way exists.

## 6. Install (`scripts/install.sh`, `scripts/merge-mcp-json.py`)

Agent files are **not merged, they are replaced wholesale**: `install.sh` replaces `.opencode/agents/` as a tree (the same rsync-with-delete rule as every other derived folder). A test (`InstallReplacesAgentFilesWholesaleTests`) installs, edits an agent file (removes the denies, re-allows a denied tool), adds an own agent file, runs `--update`, and asserts that the shipped file is back byte for byte and that the own file under `.opencode/agents/` is gone. So the denies return with every update and a user edit of a generated agent file does not survive; an own agent file belongs outside `.opencode/agents/` or in another config location. The MCP config merge (`merge-mcp-json.py`) is unchanged: `opencode.json` is a byte-identical fixed point of a second `--update` (tested), and SEC-T658-05 (a) to (d) are untouched.
