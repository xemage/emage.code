# plan-060 — v7.0 release readiness and closure

**Status: proposed — review pass only, no task authored yet.**
Based on: `docs/plans/plan-035-roadmap-v7-ground-up.md` (master roadmap), `docs/plans/plan-055-phase6-closed-loop-rescoped-detailed-planning.md`, `docs/checkpoints/checkpoint-033-phase4-phase5-complete-gate-g3-closed.md`, `docs/checkpoints/checkpoint-034-phase6-six-task-implementation-complete.md`, `docs/artifacts/phase6-sia-readiness-audit-v1.md`, `docs/plans/plan-054-codex-platform-integration-post-v7.md`.

## 0. Why this document exists

The user asked to review the v7 roadmap and plan what's left to actually release v7.0. Phase 6's
six originally-scoped tasks (`T501`–`T506`, `plan-035` nominal `T460`–`T466`) are done, merged, and
independently verified — that much is settled and recorded in `checkpoint-034`. This document goes
one level up: it checks that work against `plan-035`'s own literal, written acceptance criteria and
gate definitions for the phase that is explicitly named `v7.0.0` in the roadmap header
(`"Phase 6 — Closed Loop (v7.0.0, ~4–6 weeks)"`), plus the roadmap's other tracks and its release
mechanics, to determine what genuinely remains.

**Bottom line: v7.0.0 is not releasable yet.** The six components exist and are individually
correct, but Phase 6's own three most substantive acceptance criteria require a *real* end-to-end
cycle to have actually run and produced a *real* accepted change — and none has. `checkpoint-034`
already flagged this honestly; this document turns that flag into a concrete task list.

## 1. What `plan-035` actually requires for Phase 6 / v7.0.0

Verbatim from `plan-035` §2.4 Phase 6 (lines 678–687 of the roadmap document):

```
- [ ] One complete cycle runs end-to-end and produces a merge request
- [ ] Improvement is measurable on the held-out suite, not only the open suite
- [ ] A proposal that touches tests/golden/** or scripts/scorecard.py is rejected automatically
- [ ] Evaluator hash is recorded in every scorecard and compared across runs
- [ ] Lineage document exists for every accepted change
- [ ] Kill switch verified by test
```

Status of each, checked against the real repo state (not the implementers' self-reports):

| AC | Status | Evidence |
|---|---|---|
| One complete cycle runs end-to-end and produces an MR | **NOT MET** | The only end-to-end run that exists is MR !341 — a deliberate mechanism-proof the top-level session ran by hand-constructing a `promote=True` `PromotionResult` and calling `open_promotion_mr()` directly. It proved the *plumbing* works. It was explicitly not a real failure→cluster→proposal→validation→promotion chain, and it was closed without merging. No real accepted change has ever gone through this loop. |
| Improvement measurable on held-out suite | **NOT MET** | Not attempted. No real proposal has ever been validated against `tests/golden/held-out/` via `promotion.py`'s real `evaluate_promotion()` path with a genuine before/after scorecard. |
| Protected-path proposal auto-rejected | **MET** | `classify_target_path()` in `meta_improver.py` raises on any path outside the four allowed harness-surface classes, proven by AST scan + adversarial tests (T503); `mr_gate.py` commits only `proposal.target_path`, so a rejected proposal never reaches git at all (T505). Structural, not just tested-once. |
| Evaluator hash recorded in every scorecard, compared across runs | **PARTIALLY MET** | `evaluator_hash.py` + `evaluator-hash-known-good-v1.json` (T504) implement the check correctly and the bug found during verification (the `__pycache__` contamination) is fixed. But "recorded in every scorecard" describes a standing pipeline behavior, and no real scorecard has been generated by a real run yet to confirm the field is actually populated in practice, only in unit tests. |
| Lineage document exists for every accepted change | **NOT MET (vacuously)** | T506 built the template and a clearly-labeled illustrative example only, correctly, because zero real accepted changes exist. This AC cannot be met until the first one does. |
| Kill switch verified by test | **MET** | `kill_switch.py` + 15 tests (T502), independently re-verified. |

**Three of six ACs are unmet, and they're the load-bearing ones** — the other three (protected-path
rejection, hash-in-scorecard, kill switch) are properties of the code; the unmet three are properties
of *having actually run the loop for real*. `plan-035` wrote the phase this way deliberately: Gate G4
exists specifically because a closed improvement loop that has never been exercised end-to-end is
unproven, not because the six components don't compile.

## 2. Gate G4 itself

`plan-035` §2.2: *"G4 — Autonomy: No closed improvement loop until G1's evaluator is version-pinned,
held-out sets exist, and the evaluator lives outside any agent's write scope."* This is Phase 6's
**entry** precondition, not its exit criterion, and it is satisfied:

- Evaluator version-pinned: `evaluator_hash.py`'s tamper-evidence check (T504).
- Held-out sets exist: `tests/golden/held-out/` (6 cases), isolation enforced by
  `tests/functional/test_golden_held_out_isolation.py`.
- Evaluator outside agent write scope: `docs/artifacts/protected-paths-v1.md`'s three-control model
  (T412 path guard, T504's hash check, T416 write-scope exclusion), all independently verified.

So the project was correctly allowed to *enter* Phase 6 and build its components. What's missing is
proof the phase's own *output* — a working closed loop — actually closes, per §1 above.

## 3. Track C — CWSO 1.0

`plan-035` §2.5: a separate repo, explicitly parallel, coupled to this plan only at three named
points (T403 deployment docs, T420 MCP contract, T41C/T415 taxonomy). **Track C is not a precondition
for releasing emage.code v7.0** — the roadmap's own structure treats it as an independent track with
named contact surfaces, not a phase this repo's version number depends on. This review did not
re-audit CWSO's own internal state (it lives in a separate repo, `/home/emage/Code/emage/CWSO`, never
touched this session) because nothing in `plan-035` makes it a release blocker. Recommendation: leave
it out of v7.0's scope entirely, note the three coupling points as still-open contract items to
verify whenever CWSO 1.0 work resumes, and don't let it delay this release.

## 5. Release mechanics (mechanical readiness, separate from roadmap readiness)

Checked directly, not assumed:

- Real tags exist through `v6.10.0` (`git tag -l`); no `v7.0.0` tag exists yet.
- `CHANGELOG.md` header says it is CI-regenerated on tag push — mechanism exists, untested this
  session.
- `/prepare-release` (`.claude/commands/prepare-release.md`) defines the real release procedure:
  version bump → changelog generation from `completed-tasks.md` → release checklist → release
  checkpoint (`docs/checkpoints/checkpoint-release-v<version>.md`) → structured `RELEASE VERDICT`
  (PASS/CONDITIONAL_PASS/FAIL). This is a well-defined, low-risk mechanical process once the
  substantive work is done — it is not itself a blocker, just the last step.
