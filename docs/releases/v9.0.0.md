# Release v9.0.0

## Summary

v9.0.0 is a MAJOR release of the emage.code harness since v8.0.0. It removes Cursor as a supported platform (ADR-010) and the shipped `github` MCP server, gives every GitLab-holding agent a named tool set instead of the whole server, adds per-agent denies to the generated Opencode agent files, changes the Pi placeholders and the GitLab entry (permission mode, a token file kept in memory), adds the two security servers to GitHub Copilot, launches Brave with `--transport stdio`, and makes a plain install merge existing configs. Read the Migration Guide before you run `--update`: items M-1 to M-4 need action first.

## Install

Latest release: v9.0.0

Install with the installer from a clone of this repository:

```bash
git clone https://gitlab.com/em-age/emage.code.git
cd emage.code
scripts/install.sh --target <your-project> --platform <name>
```

| Platform | `--platform` value |
|----------|-------------------|
| GitHub Copilot (VS Code) | `github` |
| Gemini CLI | `gemini` |
| Opencode | `opencode` |
| Pi | `pi` |
| Claude Code | `claude-code` |
| Cline | `cline` |
| All platforms | `all` |

Cursor support was removed in v9.0.0; see Migration Guide item M-1.

Update an existing install: add `--update`. `scripts/install.sh --help` lists every option. If you run v7.x or older, first read the Migration Guide of v8.0.0 (`docs/releases/v8.0.0.md`, in this tree and at the `v8.0.0` tag); its item M-9 still applies to you.

Set the MCP environment variables named in the generated MCP config, then run
`/new-project "Your idea"` in your assistant.

## Highlights

- **Cursor is no longer supported (ADR-010, T662, T678).** `--platform cursor` exits 1 before anything is written, and `--platform all` no longer writes `.cursor/`. A leftover `.cursor/` is frozen and its agents are not tool-restricted: read M-1.
- **No agent holds the whole `gitlab` server any more (T666, T667, T688).** The seven holder roles have named tool sets; none of them can merge, approve, push, tag, release or control pipelines through MCP. The top-level session merges and tags, with the user's approval.
- **GitLab token in memory (T665, T689).** The generated `gitlab` entry reads a token file (`GITLAB_PERSONAL_ACCESS_TOKEN_FILE`), kept by default in memory, and sets `GITLAB_PERMISSION_MODE=modify`. The new `scripts/check-gitlab-token.py` checks the token without printing it.
- **Opencode per-agent denies (T663).** Each generated Opencode agent can call only the MCP servers it is granted, plus the read and search servers that are exempt.
- **GitHub Copilot gets the security servers (T690).** `security-audit` and `poc-security-audit` are now in `.vscode/mcp.json`, so the PoC security scan can complete on Copilot (closes v8.0.0 K-3).
- **The `github` MCP server is removed (T676).** Docker no longer launches any shipped server.
- **Brave is launched with `--transport stdio` (T712).** An environment variable or a `.env` file can no longer switch it to HTTP (observed by the user on 2026-11-01).
- **Safer installs (T672, T682, T684).** A plain install merges existing configs instead of overwriting them, every config is validated before the first write, writes are atomic, and an interrupted run is detected.
- **Maturity.** All 28 agents are `stable`; `orchestrator` was promoted in this cycle (T670).

## Breaking changes

Counting rule (release manager): this section lists every task that `docs/artifacts/release-v9-audit-v1.md` §1.3 classifies as **breaking**, one entry per task (8 entries: T662, T663, T665, T666, T667, T676, T680, T688). Behaviour changes that the audit classifies as **behaviour** (T672, T675, T682, T684, T689, T690, T692, T693, T694) and the Brave launch change of T712 are in the Migration Guide and are not counted here. The verdict count equals the number of entries listed here.

- **A-01** Cursor is no longer a supported platform (T662, ADR-010). `scripts/install.sh --platform cursor` exits 1 before writing anything; `--platform all` no longer installs `.cursor/`. The `cursor` platform manifest, the generated `.cursor/` tree (agents, commands and rules as `.mdc`, skills, `mcp.json`) and the `cursor` MCP format value are removed. Maintainers with a platform manifest that sets `mcp.format` to `cursor` must change it (Pi now uses `pi`). `pack.json` `supportedPlatforms` no longer accepts `cursor` (M-1).
- **A-02** (Opencode only) Every generated `.opencode/agents/*.md` gets `false` entries: the six unsafe Playwright tools for every agent, and `<server>_*: false` for every non-exempt server that the agent holds no tool of. `filesystem`, `git` and `supabase` are denied to every generated agent (T663, M-7).
- **A-03** (narrow) The generated `gitlab` entry sets `GITLAB_PERMISSION_MODE=modify`: the pinned server refuses its delete tools and teardown tools in every session of that client, your own included. The entry also gains `GITLAB_PERSONAL_ACCESS_TOKEN_FILE`; the Claude Code placeholders become `${VAR:-}` and the Gemini CLI placeholders `${VAR}` (T665, M-5).
- **A-04** `orchestrator` (16 tools) and `poc-orchestrator` (8) hold named GitLab tools instead of the whole server: no merge, approve, tag, release or pipeline control (T666, M-6).
- **A-05** `devops-engineer` (11), `release-manager` (17) and `poc-devops-engineer` (6) likewise; no agent holds the whole `gitlab` server (T667, M-6).
- **A-06** The `github` MCP server (container `ghcr.io/github/github-mcp-server`, `GITHUB_PERSONAL_ACCESS_TOKEN`) is removed from `servers.yaml` and from every generated config; `--update` prunes the generator-owned name `github` (T676, M-2).
- **A-07** (Pi only) `.pi/mcp.json`: placeholders change from `${env:X}` to `${X}`; the optional GitLab token variables are left out of the entry (Pi reads them from its environment); `hindsight` and `cwso` are no longer generated for Pi and the update prunes them (T680, M-4).
- **A-08** (narrow) `qa-engineer` loses `get_pipeline_job_output` (20 to 19 GitLab tools) and must not read raw CI job traces by any route (T688, M-6).

## Migration Guide

**Migration from v8.0.0 to v9.0.0.** Read M-1 to M-4 **before** you run `scripts/install.sh --update`: M-2 and M-4 need action first, and M-1 tells you what happens to an existing `.cursor/`. M-5 to M-10 and M-12 apply after the update; M-11 is for maintainers of the source repository. The installer renames or deletes nothing in your project except the platform trees and generator-owned MCP entries it owns. Everything marked **(not re-run)** was taken from a repository document or from code reading and was not re-run by the release manager.

```bash
git -C <emage.code clone> pull        # or check out the v9.0.0 tag
scripts/install.sh --target <your-project> --platform <name>|all --update
```

`<name>` is one of `github`, `gemini`, `opencode`, `pi`, `claude-code`, `cline`.

**M-1. Cursor is no longer supported (ADR-010; T662, T678, T679; SEC-T662-01, SEC-T678-03).** Nothing is required before `--update`; the steps below remove what an earlier release left in `.cursor/`.

- **What changed.** `scripts/install.sh --platform cursor` exits 1 before writing anything and names this item; the v8.x releases are the last that support Cursor. `--platform all` no longer installs `.cursor/`. The `cursor` platform manifest, the generated `.cursor/` tree and the `cursor` MCP format value are removed. `--update` and `--projections-only` no longer touch `.cursor/` at all: files you added there are no longer deleted (before, they were), and the installer never deletes the folder.
- **The installer warns on `--update` and `--projections-only`.** When it finds a harness-generated `.cursor/` (a `.cursor/.generated-manifest.json` for platform `cursor`, or a `.cursor/mcp.json.provenance.json`) it prints a warning that names the `filesystem` entry, the keys `e2b`, `redis`, `figma` and `notion`, and this item (`scripts/install.sh:1285-1302`). A plain install without `--update` prints nothing about it.
- **A leftover `.cursor/` is frozen (SEC-T678-03).** It is no longer updated, pruned or checked. Its MCP server versions are frozen at the release that wrote it and are not bumped, its Playwright hardening is not updated, and its agents and rules are not refreshed. **Its agents are not tool-restricted: in Cursor every agent can call every tool of every configured server**, including the GitLab write tools and the unsafe Playwright tools, because Cursor has no deny mechanism that the harness writes (as in v8.0.0, SEC-T658-01).
- **If you do not use Cursor with this harness, or want a clean tree:**
  1. If you added nothing of your own to `.cursor/`, delete the folder: `rm -r .cursor`.
  2. If you did, delete the paths listed under `files` in `.cursor/.generated-manifest.json`, except `mcp.json`; then delete the manifest and any empty folders.
  3. In `.cursor/mcp.json`, remove the server entries the harness added (the names listed under `generatorOwnedKeys` in `.cursor/mcp.json.provenance.json`) and keep your own, or delete the file if nothing in it is yours. Then delete the sidecar `.cursor/mcp.json.provenance.json`.
- **If you keep the folder, remove the dangerous entries now (the steps of M-9 of the v8.0.0 release notes, for `.cursor/mcp.json`).** Edit `.cursor/mcp.json` by hand:
  1. Remove the `filesystem` server object if it runs `npx -y @anthropic/mcp-filesystem`. Every release from `v5.0.0` to `v7.0.1` shipped it. That package does not exist on npm, and the `@anthropic` npm scope is not controlled by Anthropic PBC (v8.0.0 M-9, research of 2026-10-14; not re-checked): whoever controls that scope can publish a package of that name, and the next launch of your assistant would run it with access to your files. Remove the entry; do not replace it (decision D-T710-1 of the release manager, SEC-T709-04). The only launcher this harness ever pinned for it, the v8.0.0 `npx -y @modelcontextprotocol/server-filesystem@1.0.0 .`, has two MODERATE advisories through `glob` and `minimatch` that are not accepted (K-17); in `.cursor/` every Cursor agent could call it, because Cursor applies no tool restriction of this harness; and this frozen copy is never updated by the installer, so it would keep that pin and those advisories. If you still add a filesystem server to Cursor, it is your own entry, outside this harness.
  2. Remove the keys `e2b`, `redis`, `figma` and `notion` if present. Every release from `v5.0.0` to `v6.9.0` shipped them unpinned: `e2b-mcp` is not published on npm and its name is unscoped, so anyone can claim it; `redis-mcp` is an unrelated third-party package; `@figma/mcp` and `@notion/mcp` are not published (v8.0.0 M-9, checked with `npm view` on 2026-10-15; not re-checked).
  3. Replace or remove the other launchers that name packages which do not exist on npm, if your file still has them: `git` running `@modelcontextprotocol/mcp-git`, `github` running `@github/mcp-github` and `supabase` running `@supabase/mcp` (v7.x installs; v8.0.0 M-9).
  4. A `.cursor/mcp.json` written by v8.0.0 also holds the `github` container entry that v9.0.0 removes everywhere else (M-2): remove it if you do not use it, and then revoke or unset `GITHUB_PERSONAL_ACCESS_TOKEN`.
- **`--force-prune-keys` is only available from the `v8.0.0` tag for a Cursor file, and it does not help here: edit the file by hand.** The option belongs to `scripts/merge-mcp-json.py` and still exists in v9.0.0, but for `.cursor/mcp.json` it needs as `--source` the generated Cursor file `implementation/.cursor/mcp.json`, which exists only at the `v8.0.0` tag (and earlier tags) of your clone. With that file, a run that names `filesystem` in `--force-prune-keys` is refused: it prunes only keys that the source lacks, that file has a `filesystem` key, so the run exits 1 and writes nothing. A run that leaves `filesystem` out does write, and merges every entry of that file, `github` included, into yours (`scripts/merge-mcp-json.py:457-471` and `:526-529`, code reading and the Tech Lead's reading in TL-T708-03; **(not re-run)**). Neither run removes the `filesystem` entry. This matches the installer's own advice (`scripts/install.sh:1300`). Decision D-T700-3 of the release manager: hand editing only.
- **The other platforms' MCP files.** The same `filesystem` launcher and the four keys may also sit in the MCP files of the platforms you still use. `--update` overwrites the generator-owned `filesystem` entry in place there; the four keys are pruned only through a provenance sidecar that lists them, which no sidecar ever did, so remove them by hand as in v8.0.0 M-9 (K-19).
- **Cursor still reads `AGENTS.md`.** Cursor reads an `AGENTS.md` in the project root (Cursor documentation, checked 2026-10-16 for ADR-010; not re-checked). The installer still writes `AGENTS.md` for every platform; its skill and rule paths name the platforms you install. The harness no longer provides Cursor-specific agents, commands, rules or skills.
- **Automation.** A script that runs `install.sh --platform cursor` now fails with exit 1 and a message. A script that runs `--platform all` and then reads `.cursor/` must be changed.
- **Rollback.** Running the v8.x installer with `--update` recreates `.cursor/` and, as before, replaces it wholesale: your own files in it are deleted by that older installer, so commit or back them up first.
- **Pack authors and maintainers.** `supportedPlatforms` in `pack.json` no longer accepts `cursor` (`implementation/registry/package.schema.json` lists the six supported platforms). A platform manifest with `mcp.format: "cursor"` now fails with `Unknown MCP format` (`implementation/scripts/sync.mjs`); Pi uses `pi`.
- Known Issue K-22 records that a Cursor install left in a project is frozen and is not pruned.

**M-2. The `github` MCP server is removed (T676, T685; SEC-T676-13).** Act **before `--update`** if you use it.

- What changed: the shipped `github` entry (container `ghcr.io/github/github-mcp-server`, `GITHUB_PERSONAL_ACCESS_TOKEN`) is gone from `servers.yaml` and every generated config. Docker no longer launches any shipped server, and the Docker prerequisite is gone from `implementation/PREREQUISITES.md`.
- Before `--update`: copy the `github` entry from your installed config under your own server name (for example `github-mine`). The update removes only the generator-owned name `github`, through the provenance sidecar.
- Without a sidecar nothing is pruned and the entry stays: delete it by hand, or run once per file `python3 scripts/merge-mcp-json.py --source <generated file> --dest <your file> --force-prune-keys github`. `<generated file>` is the file of your clone that matches your platform: `implementation/.mcp.json` (Claude Code), `implementation/.vscode/mcp.json`, `implementation/.gemini/settings.json`, `implementation/.opencode/opencode.json`, `implementation/.pi/mcp.json`, `implementation/.cline/mcp.json` (`docs/wiki/mcp-servers.md`, "Migrating an existing install", item 8). A name that is not in a file is refused with exit 1 and nothing is written: skip it.
- A GitHub server that you keep under your own name is outside every generated denial on Opencode and Gemini CLI (those denials name the generated servers only), so give it a fine-grained, read-only token. If you no longer use a GitHub server, revoke or unset `GITHUB_PERSONAL_ACCESS_TOKEN`.
- The harness ships no GitHub tooling any more; your own session keeps whatever you configured yourself.

**M-3. A plain install merges existing configs; new file names and refusals (T672, T682, T684; SEC-T672-06).**

- What changed: `scripts/install.sh` **without** `--update` over an existing MCP or settings config now merges it, as `--update` does, instead of overwriting it. Every existing config is validated as JSON before the first write; an invalid one stops the run, naming the file, with nothing written.
- With no provenance sidecar the merge prints: `merge-mcp-json: note: <dest>: there is no provenance sidecar at <old-sidecar>, so no retired generator entry could be pruned; kept your server(s) a, b, which the generated config does not contain. If one is a retired generator entry, remove it by hand or run scripts/merge-mcp-json.py with --force-prune-keys <name>.`
- New names on disk: `.<name>.<random>.tmp` (atomic writes), `<ledger>.bak`, then `.bak.2`, `.bak.3` (the task-ledger merge), and `<tree>.emage-new.<pid>` and `<tree>.emage-old.<pid>` (the tree swap).
- A leftover `.emage-old.<pid>` or `.emage-new.<pid>` from an interrupted run stops the next run with `error: a previous update of this target was interrupted ...` and a restore hint; nothing is written or removed. If the managed folder is missing, the `.emage-old` sibling is your only copy: restore it with the printed `mv` line.
- An option value that starts with `-` (for example `--target -x`) is refused; write `./-x`. `--dry-run` creates nothing **(not re-run)**.

**M-4. Pi: placeholder form, GitLab variables, `hindsight` and `cwso` (T680).** Act **before `--update`** if you edited `hindsight` or `cwso` in `.pi/mcp.json`.

- Before `--update`: copy a hand-edited `hindsight` or `cwso` entry to another name. The update removes those two names from `.pi/mcp.json` ("pruned the retired generator server"). Pi 1.x rejects a templated URL, so add your own entry with a literal URL if you need them.
- After: every placeholder in a generated entry changes from `${env:X}` to `${X}` (Pi 0.99.0 to 1.4.0 kept `${env:X}` as literal text, so those entries never worked). A server entry of your own that uses `${env:X}` is kept unchanged and without a note, and Pi does not expand it: convert your own entries to `${X}` by hand (QA-T707-02). The `gitlab` entry no longer carries `GITLAB_PERSONAL_ACCESS_TOKEN` or `GITLAB_PERSONAL_ACCESS_TOKEN_FILE`: export one of them in Pi's environment, because Pi fails the whole server on an unset or empty variable. Prefer `GITLAB_PERSONAL_ACCESS_TOKEN_FILE`, which holds the **path** of a token file kept in memory (M-5), not the secret. Never put the token itself in a shell profile or a `.env` file on an unencrypted disk: it would be a plaintext secret at rest (Immutable Security Constraint 6; SEC-T709-03).
- The update drops retired `${env:` keys with a note ("dropped the retired `${env:` entry") and keeps any other key of yours. A key with a credential-like name and a literal value prints `WARNING: ... holds a literal value; remove it from the file and revoke the token` (names only, never the value): remove it and revoke that token.

**M-5. GitLab entry: permission mode and the token file in memory (T665, T689, T701).** After `--update`.

- The generated `gitlab` entry sets `GITLAB_PERMISSION_MODE=modify`: the pinned server refuses every delete tool and teardown tools such as `cancel_pipeline` **in every session of that client, your own included** (the teardown list is from the server README on main, not matched to 2.2.5 **(unverified)**). To lift it, edit your client config; `--update` writes the generated value back. Lifting it applies to every agent of that client: on clients whose agent tool lists do not restrict MCP tools (Gemini CLI, and Opencode's built-in agents and agent files of your own, K-15, K-23), every such agent regains the delete and teardown tools. Prefer `glab` or the GitLab web UI for such an operation instead of lifting the mode (SEC-T709-02).
- The entry gains `GITLAB_PERSONAL_ACCESS_TOKEN_FILE`. On Claude Code both token placeholders become `${VAR:-}`: leave them as they are. On Gemini CLI the placeholders change from `${env:VAR}` to `${VAR}`. Claude Code asks you to approve the changed project server again.
- Nothing breaks if you do nothing: an exported `GITLAB_PERSONAL_ACCESS_TOKEN` keeps working. An export of the token in a shell profile file, or in a `.env` file that your shell reads, is a **plaintext secret at rest**. The environment mode stays supported, but on an unencrypted disk such an export is not acceptable (Immutable Security Constraint 6, which admits no acceptance); a variable filled at login from an in-memory or encrypted store is not data at rest (`implementation/PREREQUISITES.md`, "File mode", step 3, T701). D-11 of `docs/artifacts/tracked-debt-register-v3.md` (TD-T697-08) is settled: the Security Engineer ruled it LOW, with no user decision needed (`docs/artifacts/security-review-t697-t699-debt-checkpoint-refresh-v1.md`; SEC-T709-01).
- To adopt file mode (recommended), follow `implementation/PREREQUISITES.md`, "File mode": write the token to a mode 0600 file **in memory** (`$XDG_RUNTIME_DIR`, else `/dev/shm`, or filled from a keyring or an encrypted store), outside every project, with the snippet given there, which removes and never follows an existing name at the token path (SEC-T689-01); export the **path** in `GITLAB_PERSONAL_ACCESS_TOKEN_FILE`; remove the old export of the token; run `python3 scripts/check-gitlab-token.py` from an emage.code checkout; revoke the old, broader token. A token file on a persistent disk is acceptable only on a disk you encrypted.
- `check-gitlab-token.py` exits 1 with a warning for a token file on a persistent file system. Automation that treats exit 1 as failure fails for a disk-resident file. Where no mount table can be read it skips that check and does not warn. It does not check the token's role in the usual case: check Planner, Reporter or Developer on the project's Members page.
- After changing the token or the file, restart the client; on VS Code Remote SSH or dev containers restart the VS Code server (observed on Claude Code in VS Code Remote SSH only).
- If you use `GITLAB_TOKEN` with `glab`: empty `glab`'s own stored login and revoke its OAuth authorization (user action A-10 of the register).

**M-6. GitLab grants of the seven holder roles (T666, T667, T688).** After `--update`.

- No agent holds the whole `gitlab` server. The named sets: `scrum-master` 24, `qa-engineer` 19 (was 20), `release-manager` 17, `orchestrator` 16, `devops-engineer` 11, `poc-orchestrator` 8, `poc-devops-engineer` 6 (line 4 of `implementation/knowledge/agents/<role>.md`, counted). `create_merge_request` is the only write tool, held by `orchestrator`, `poc-orchestrator` and `release-manager`. No agent holds merge, approve, push, file write, delete, branch, tag or release creation, pipeline trigger, retry or cancel, CI variables or raw job output.
- `orchestrator`, `poc-orchestrator`, `devops-engineer`, `release-manager` and `poc-devops-engineer` held the whole server in v8.0.0. A workflow in which one of them merged, tagged, released or ran pipelines through MCP must move to the top-level session or to you.
- `qa-engineer` loses `get_pipeline_job_output` and must not fetch raw CI job traces by any route (MCP, `glab ci trace`, `curl`, a `/raw` URL, the browser); its bug reports carry a log excerpt that the user checked.
- This narrows tool lists; it is not a credential boundary. Six of the seven roles hold `execute`, and a shell that holds the token can call the API (K-16). Existing installs keep the old grants until `--update`.

**M-7. Opencode: per-agent denies in the generated agent files (T663).** After `--update`.

- Each generated `.opencode/agents/*.md` gets `false` entries: the six unsafe Playwright tools for every agent, and `<server>_*: false` for each server marked `denyUnlessGranted` that the agent holds no tool of (`gitlab`, `playwright`, `memory`, `sequential-thinking`, `security-audit`, `poc-security-audit`, `context-retriever`, `filesystem`, `git`, `supabase`). No agent lists `filesystem`, `git` or `supabase`, so generated agents can no longer call them on Opencode. Exempt and still reachable: `brave`, `context7`, `hindsight`, `cwso`, `hf-mcp-server`, `toolradar`.
- Not covered (user decision 2026-10-16, "No, document the gap only"): Opencode's built-in agents and agent files of your own (K-23).
- A global `ask` or `deny` of yours on a tool that an agent holds is overridden for that agent; only `OPENCODE_CONFIG_CONTENT` (observed) or a managed configuration (source reading) is applied later (`AGENTS.md`, "MCP Servers").
- `--update` replaces `.opencode/agents/` as a tree; edits there are lost.

**M-8. GitHub Copilot: two code-launching servers are added (T690; SEV-T690-07).** After `--update`; **the installer prints nothing about it.**

- `--update` adds `security-audit` and `poc-security-audit` to `.vscode/mcp.json`: `python3 -m implementation.runtime.security.audit_server` and `python3 -m implementation.runtime.security.poc_audit_server --allowed-root .`, each with `"cwd": "${workspaceFolder}"`, no environment entries and no secret.
- They run Python code from the workspace (`implementation/runtime/security/`, copied by the installer); a hostile branch can change that code (SEV-T690-02, the same exposure as on the other five platforms). They need `mcp==2.2.0` in the `python3` that VS Code starts: in a virtual environment, `pip install --require-hashes -r implementation/runtime/security/requirements-mcp-server.lock.txt`.
- VS Code's Workspace Trust and tool-approval prompts for them were not observed **(unverified)**. Both names are generator-owned: a hand removal is undone by the next update, and an entry of your own with one of these names is overwritten in place (inferred from the provenance merge rules; **(not re-run)**).
- The Copilot agents `security-engineer` and `poc-security-engineer` already held the tools; the PoC security scan can now complete on Copilot (v8.0.0 K-3 closed).
- Decision D-T700-5 of the release manager: these release notes carry the notice; an installer note on `--update` stays tracked LOW debt (SEV-T690-07).

**M-9. Release gate input (T693).** For teams that use `release-manager`.

- A `PASS` or `CONDITIONAL_PASS` release verdict now needs a row in the Gate Inputs table naming who checked the release document independently (the `tech-lead` review by area, or the top-level session's own verification) and the commit that check covered. After that check only the release verdict section and the `Release:` line under the gate verdicts may change; any other change makes the check stale, and the same party re-runs it (`implementation/knowledge/agents/release-manager.md`, Release Gate Policy item 5).

**M-10. Behaviour changes to brief your team on (no action).**

- The installed `security-audit` tools refuse paths with a secret-bearing component (`.env`, `.env.example`, `.envs/`, `prod.env`, private keys, certificates, credential files, `.git`), deny by default, so a legitimate file such as `monkey.key` is refused too; git worktree roots are accepted (T675).
- The shipped `playwright` entry blocks 39 origins (was 22; T676); a `playwright-local` entry of your own is unchanged.
- PoC: `TECHNICAL-DEBT.md` lives in the PoC root next to `POC-DEBT-SCORECARD.md` (T692).
- All 28 agents are `stable` (T670).
- Hash-locked requirements exist for the two Python MCP runtimes: `implementation/runtime/memory/requirements-mcp-server.lock.txt` and `implementation/runtime/security/requirements-mcp-server.lock.txt` (`pip install --require-hashes -r ...`); the plain `requirements-mcp-server.txt` adds the floor `httpx2>=2.12.0` (T676, SEC-T646-04).
