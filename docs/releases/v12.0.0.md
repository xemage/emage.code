# Release v12.0.0

## Summary

v12.0.0 is a MAJOR release of the emage.code harness since v11.0.0. On Opencode, every generated agent now carries a `permission:` map built from its source: an agent that does not hold a shell, edit, web or delegation tool is denied it, the two orchestrators can launch only their named subagents, and the 13 agents without a shell are denied reads of the default GitLab token directory. The release also moves the Brave pin to 2.1.5, which fixes SEC-T702-09, and the `filesystem` pin to 2.4.0. Read the Migration Guide before you run `--update`: M-1 to M-3 if you use Opencode, M-4 for the MCP pins and Node, and M-6 if you script the memory index build.

## Install

Latest release: v12.0.0

Install with the installer from a clone of this repository:

```bash
git clone https://gitlab.com/em-age/emage.code.git
cd emage.code
scripts/install.sh --target <your-project> --platform <name>
```

| Platform | `--platform` value |
|----------|-------------------|
| GitHub Copilot (VS Code) | `github` |
| Opencode | `opencode` |
| Claude Code | `claude-code` |
| Cline | `cline` |
| All platforms | `all` |

Pi and Gemini CLI support was removed in v11.0.0; see Migration Guide items M-1 and M-2 of `docs/releases/v11.0.0.md`. Cursor support was removed in v9.0.0.

Update an existing install: add `--update`. `scripts/install.sh --help` lists every option. If you run v10.x or older, first read the Migration Guide of v11.0.0 (`docs/releases/v11.0.0.md`, in the emage.code repository and at the `v11.0.0` tag), and for older releases those of v10.0.0 and v9.0.0 as well.

The MCP servers launched through `npx` need Node.js 22 (22.23.5 or later), 24 (24.22.3 or later) or 26 (26.13.1 or later). The opt-in `filesystem` server's pin declares Node 24 or later (M-4).

Opencode: use opencode-ai 1.0.224 or later, 1.x (M-3).

Set the MCP environment variables named in the generated MCP config, then run
`/new-project "Your idea"` in your assistant.

## Highlights

- **Opencode agents get real permission maps (plan-168, plan-175, plan-178; SEC-T840-01 fixed).** Each generated `.opencode/agents/*.md` carries a `permission:` map instead of the `tools:` block that Opencode did not read as permissions. An agent whose source holds no shell, edit, web or delegation tool is denied `bash`, `edit`, `webfetch`/`websearch` or `task`. In v11.0.0 every generated agent kept Opencode's defaults for these keys; that gap, SEC-T840-01, shipped in v11.0.0 and is fixed in v12.0.0. Read M-1 and M-2.
- **Opencode orchestrators delegate only to their own team (SEC-T844-01).** `orchestrator` and `poc-orchestrator` can launch only the 14 subagents named in their sources, not Opencode's built-in agents or an agent file of your own (M-1).
- **Token-directory denies on Opencode (SEC-T842-02, SEC-T856-02).** The 13 generated agents without a shell are denied `read` and `external_directory` on the default `gitlab-mcp` token directory. These denies are defense in depth, not a boundary (M-1, K-42).
- **Brave 2.1.5 and `server-filesystem` 2.4.0 (SEC-T702-09, SEC-T756-07).** The Brave pin's seven known advisories are retired, so the v11.0.0 acceptance K-28 closes with no new acceptance. The `filesystem` pin no longer resolves the affected `glob` and `minimatch`, and declares Node 24 or later (M-4).
- **The installer no longer skips a changed file of equal size (TD-T774-01, QA-T818-01).** `install.sh` copies with `rsync --checksum`, so the first `--update` with this release repairs a stale file, and v11.0.0's lock-file check and `touch` workaround are no longer needed (M-5; K-39 closed).
- **One accepted risk, with a new acceptance for v12.0.0 (ADR-011, ADR-015, ADR-016).** K-16 (SEC-T660-01, SEC-T665-01, the GitLab token) ships under the user's acceptance for v12.0.0 only, after the Security Engineer's dated confirmation T871 that no harness fix exists (Known Issues).

## Breaking changes

Counting rule (release manager): this section lists, one entry per change, every change of `docs/artifacts/release-next-audit-v1.md` § 1 that removes a capability an existing install had, refuses an input or a client an earlier release accepted, or changes what an existing install's sessions see (B-1 to B-6, B-8 and B-12; 8 entries: A-01 to A-07 for a target, A-08 for a fork that authors its own knowledge). The verdict count equals the number of entries listed here. The other changes of that section are under Changelog and in M-5 to M-10, and are not counted.

- **A-01** Opencode: every generated agent file carries a `permission:` map with `allow`/`deny` values instead of the generic `tools:` block, and the per-agent MCP denies of T663 move into the same map (B-1, M-1).
- **A-02** Opencode: an agent whose source does not hold `execute`, `edit`, `web` or `agent` gets `bash: deny`, `edit: deny`, `webfetch: deny` and `websearch: deny`, or `task: deny`. In v11.0.0 these agents had Opencode's defaults. 13 generated agents carry `bash: deny` and 26 carry `task: deny` (re-counted by the Tech Lead at `90124fb6`, T876 TL-T876-05; each orchestrator carries 14 named `task` allows after `"*": deny`) (B-2; SEC-T840-01; M-1).
- **A-03** Opencode: `orchestrator` and `poc-orchestrator` get `task: {"*": deny, ...}` with an allow for each of the 14 subagents of their source `agents:` list. They can no longer launch Opencode's built-in agents (`build`, `plan`, `general`, `explore`, ...) or an agent file of your own (B-3; SEC-T844-01; M-1, M-2).
- **A-04** Opencode: the 13 generated agents without `execute` are denied `read` on `gitlab-mcp`, `gitlab-mcp/*`, `*/gitlab-mcp` and `*/gitlab-mcp/*`, and `external_directory` on `*/gitlab-mcp/*` (B-4; SEC-T842-02, SEC-T856-02; M-1).
- **A-05** Opencode: the supported client range is opencode-ai 1.0.224 up to the latest 1.x, tested on 1.19.2; earlier releases and 2.x are not supported (B-5; SEC-T837-02; M-3).
- **A-06** Memory index build: `build.py` exits 2 when `--project-id` is not exactly the lower-case `org/repo` it derives from the `origin` remote of `--own-repo-root`, or when that repository has no usable `origin` remote. v11.0.0 refused only a malformed id (B-12; QA-T818-03; M-6).
- **A-07** The opt-in `filesystem` server's pin, `@modelcontextprotocol/server-filesystem@2.4.0`, declares `engines.node` `>=24` and is built on the MCP SDK v2 packages. Whether it runs on Node 22 is **unverified** (B-8; TL-T869-01; M-4).
- **A-08** (fork authors) The manifest's `tools` enum loses `object` and gains `permission`, so a fork manifest with `tools: "object"` fails the schema and the generator; `sync.mjs` also stops on a tool list that both grants and denies a key, a non-deny rule for a deny-only key, a `task` map other than `"*": deny` plus named allows, a built-in or the agent's own name in `agents:`, and `mcpAgentDenies` without `tools: "permission"` (B-6; M-8).

## Migration Guide

**Migration from v11.0.0 to v12.0.0.** Do this in order:

1. **Before the update:** commit or back up your project, including any file you keep inside a platform tree: `--update` replaces `.github/`, `.opencode/`, `.claude/`, `.cline/` and `.clinerules/` wholesale, and `.opencode/agents/` is replaced as a tree, so an agent file of your own placed there is deleted (M-2). If you use Opencode, check your client version (M-3), and check any automation that relies on a generated Opencode agent running a shell, editing, using the web, or an orchestrator launching a built-in agent (M-1).
2. Run the update:

   ```bash
   cd <emage.code clone>
   git fetch --tags && git checkout v12.0.0
   scripts/install.sh --target <your-project> --platform <name> --update
   ```

3. **After the update:** M-1 and M-2 if you use Opencode; M-4 if you enable the `filesystem` server; M-6 if you script the index build; M-7 if you use `context-retriever` with an unusual git remote.

M-8 is for a fork that authors its own knowledge. M-9 is for someone working on releases from an emage.code checkout. M-10 needs no action. On a throwaway target installed by the v11.0.0 installer with `--platform all`, this release's `--update` exited 0, modified 36 files (the 28 generated Opencode agents, the four generated MCP configs, `AGENTS.md` and three files under `implementation/runtime/memory/`) and deleted one, an agent file of the user's own placed in `.opencode/agents/` (observed by the release manager on 2026-11-19; no assistant, MCP server or index took part).

**What a target does not receive.** The install writes no `scripts/`, `docs/releases/`, `.gitlab-ci.yml`, `CONTRIBUTING.md` or `implementation/PREREQUISITES.md`, and of `docs/wiki/` only the two project-wiki templates `docs/wiki/README.md` and `docs/wiki/home.md` (the observed target above holds only `AGENTS.md`, `CLAUDE.md`, `docs/`, `implementation/` and the platform trees; `install.sh` names none of these files, `docs/artifacts/release-next-audit-v1.md` § 8 item 6). Any `scripts/` command in this document runs from an emage.code clone, and any `docs/releases/` path, any `docs/wiki/` path other than those two templates, and `implementation/PREREQUISITES.md`, cited by M-3 and M-4, are in the emage.code repository and are not installed into a target (QA-T875-02).

**Cursor: nothing changes in this release.** No line of `scripts/install.sh` that names Cursor points to this document, so this document carries no Cursor item. The installer's Cursor notices keep pointing to the older documents: `scripts/install.sh:187` and `:1317` name the Cursor migration item in `docs/releases/v9.0.0.md`, and `:1313` holds the advice on `.cursor/mcp.json`, which names M-9 in `docs/releases/v8.0.0.md`. The Pi and Gemini CLI lines, `:192` and `:1339` (Pi) and `:196` and `:1363` (Gemini CLI), point to `docs/releases/v11.0.0.md`, correctly. No installer line points to this document (lines re-read on `release/v12.0.0`, TD-T723-01).

### M-1. Opencode: what the generated agents lose (B-1 to B-4; SEC-T840-01, SEC-T844-01, SEC-T842-02, SEC-T856-02)

After `--update`, `.opencode/agents/` is replaced as a tree (agent files are not merged) and every generated agent carries a `permission:` map:

- **Shell, edit, web and delegation.** An agent whose source does not hold `execute` gets `bash: deny`; without `edit`, `edit: deny`; without `web`, `webfetch: deny` and `websearch: deny`; without `agent`, `task: deny`. `bash`, `webfetch`, `websearch` and `task` are never written as an allow, so an agent that holds the tool keeps Opencode's default for those. `edit` is different: an agent whose source holds `edit` gets `edit: allow` (20 agents), and as the agent's own rule it overrides a global or project `edit: ask` or `deny` of yours, as for the MCP allows in `AGENTS.md` (SEC-T877-01, QA-T875-01; LOW). On v11.0.0 every generated agent had Opencode's defaults for all five keys (SEC-T840-01, shipped in v11.0.0 and never accepted; fixed in v12.0.0).
- **The orchestrators.** `orchestrator` and `poc-orchestrator` can launch only the 14 subagents of their source `agents:` list. They can no longer launch `build`, `plan`, `general`, `explore` or an agent file of your own; you still can, from your own session (SEC-T844-01).
- **The token directory.** The 13 agents without `execute` are denied `read` on `gitlab-mcp`, `gitlab-mcp/*`, `*/gitlab-mcp` and `*/gitlab-mcp/*`, and `external_directory` on `*/gitlab-mcp/*`. Not covered: a `grep` on a parent directory such as `/dev/shm` or `/run/user/<uid>`, which only that directory's `external_directory` rule guards (`ask` by default); a token at a non-default name or path; a token linked or copied into a project (register v24 § 6.2 item 49 (d); K-42).
- **What to change.** Automation or habits that relied on, for example, a reviewer agent running a shell, or an orchestrator launching `general` or `build`, must change: use a generated agent that holds the tool, or your own session.
- **Your own rules do not re-grant.** A global or project `permission` rule of yours (`allow` or `ask`) does not override a generated agent's own deny: the agent's own rules come last. Only a source that Opencode loads after the agent files can, the environment variable `OPENCODE_CONFIG_CONTENT` (observed on opencode-ai 1.19.2) and, by source reading only, the managed configuration (`AGENTS.md`, MCP Servers).
- **What is observed.** The resolved rule lists are observed on opencode-ai 1.19.2 for the agents run in the evidence runs (`docs/artifacts/mcp-agent-denials-evidence-v1.md` and later versions). A refused call and a refused launch are not observed, and the mapping of `bash`, `edit`, `webfetch`, `websearch` and `task` at call time for the agents not run rests on the generator **(unverified live; K-20)**.
- **Rollback.** The v11.0.0 installer writes the `tools:` form back (Rollback Plan).

### M-2. Opencode: built-in agents and your own agent files (K-23, unchanged)

- **Unchanged:** Opencode's built-in agents (`build`, `plan`, `general`, `explore`, ...) and agent files of your own get none of the new denies, no per-agent MCP deny and no global GitLab deny; only the server-level denial of six Playwright tools applies to them (K-23, user decision 2026-10-16, "No, document the gap only"). `build` keeps a shell, and with it the GitLab token (register v24 § 6.2 item 49 (b); K-16).
- **Changed:** the generated orchestrators can no longer launch them (A-03). You still can.
- **Your own agent files inside `.opencode/agents/` are deleted by `--update`.** The tree is replaced, not merged. This is not new in v12.0.0, but it was observed again on 2026-11-19: on the throwaway target of the Migration Guide, a file of the user's own in `.opencode/agents/` was deleted by this release's `--update`. Keep your own agent files outside the trees the installer writes; which Opencode location to use instead was not checked for this document **(unverified)**.

### M-3. Opencode client version (B-5; SEC-T837-02)

Use opencode-ai 1.0.224 or later, 1.x; tested on 1.19.2; 2.x is not supported (`implementation/PREREQUISITES.md:66`). 1.0.224 is the first release whose agent `permission` map takes wildcard keys and patterns. How an older client treats the new maps was not tested **(unverified)**; nothing in the installer checks your client version.

### M-4. MCP pins: Brave 2.1.5 and `server-filesystem` 2.4.0; Node for `filesystem` (B-7, B-8; SEC-T702-09, SEC-T756-07, TL-T869-01)

- **Nothing to do beyond `--update`** for the generated entries: `brave` moves to `@brave/brave-search-mcp-server@2.1.5` (`implementation/knowledge/mcp/servers.yaml:143`, `--transport stdio` still forced) and `filesystem` to `@modelcontextprotocol/server-filesystem@2.4.0` (`:241`). An entry of the same server that you own under another name is not touched, because the merge keeps names the generator does not own.
- **Brave:** 2.1.5 retires the seven advisories of 2.1.4, five of them graded high by npm, and is the first Brave release with SLSA provenance. SEC-T702-09 is fixed, so K-28 closes and the v11.0.0 acceptance is history. Brave 2.2.0, published on 2026-11-19, is not pinned (`docs/artifacts/mcp-pin-audit-next-v1.md` § 5).
- **`filesystem`:** 2.4.0 no longer resolves `glob` or the affected `minimatch`, so the two moderates of 1.0.0 (SEC-T756-07) are gone (`mcp-pin-audit-next-v1.md` § 1). It depends on the MCP SDK v2 packages and **declares `engines.node` `>=24`**. Use Node 24 or 26 if you enable it (`implementation/PREREQUISITES.md:4`, exception TL-T869-01). Whether `npx` refuses it on Node 22 (npm only warns about `engines` unless `engine-strict` is set) or whether it fails at run time is **unverified**. The server is opt-in, and no agent holds it.
- **Node minimums** are unchanged since v11.0.0: 22.23.5, 24.22.3 or 26.13.1 and later on their lines. Nothing in the installer or the servers checks your Node version **(unverified)**.

### M-5. Installer copy fixed; drop v11.0.0's lock-file check and `touch` step (B-11; TD-T774-01, QA-T818-01)

`scripts/install.sh` copies with `rsync -a --checksum` on both copy paths (`scripts/install.sh:938`, `:988`; comment at `:907`), so a changed file of equal size and the same-second timestamp is no longer skipped. The v12.0.0 installer, run from the new clone, already copies this way, so the first `--update` repairs a file that an earlier update left stale. v11.0.0's M-6 `grep` of the lock files and its `touch` step before every `--update` are no longer needed, and K-39 closes. The cost is a checksum pass over each tree at every install.

### M-6. Memory index build (B-12; QA-T818-03)

A script that builds the index must pass as `--project-id` exactly the lower-case `org/repo` that `build.py` derives from the `origin` remote of `--own-repo-root`, and that repository must have an `origin` remote; otherwise `build.py` exits 2 (`implementation/runtime/memory/build.py`; the install notice says so at `scripts/install.sh:1759` and `:1760`).

### M-7. `context-retriever` remotes (B-13; SEC-T829-01, SEC-T829-02, SEC-T832-01, SEC-T832-02, SEC-T835-01, SEC-T835-02)

No action for normal remotes. A remote that is not valid UTF-8, an `@` in the derived `org/repo`, a `git remote get-url` that times out (10 s) or another subprocess error now gives a clean refusal: no project id, so the server does not start (default) or `retrieve` fails (`--index-dir`), as for other unusable remotes in v11.0.0. Refusal messages no longer show userinfo, a query string or a fragment, and no longer repeat the slug.

### M-8. Generator, for a fork that authors its own knowledge (B-6)

- Change `tools: "object"` to `tools: "permission"` in an Opencode-like manifest of your own (`implementation/platforms/_manifest.schema.json`). Five Opencode-only manifest keys are new: `permissionKeys`, `permissionDenyUnlessGranted`, `permissionTaskAllowFromAgents`, `permissionReadDenyUnlessGranted` and `permissionExternalDirectoryDenyUnlessGranted` (`implementation/platforms/opencode.json`).
- `implementation/scripts/sync.mjs` stops on an agent source that both grants and denies a key, a non-deny rule for a deny-only key, a `task` map other than `"*": deny` plus named allows, a built-in name or the agent's own name in `agents:`, and `mcpAgentDenies` without `tools: "permission"`.

## Rollback Plan

**Tested for the installed files, on a throwaway target; not tested with a live client.** On 2026-11-19 the release manager installed the `v11.0.0` tree, from a `git archive` of that tag, with `--platform all` into an empty git repository, and added a file of the user's own inside `.opencode/agents/`. This tree's `--update` then exited 0, modified 36 files and deleted the user's own file. The `v11.0.0` installer's `--platform all --update` exited 0 and brought the target back to its v11 state, except for the deleted file, which it does not restore. This tree's `--update` again exited 0, and the target was identical to the first v12 state (`git diff`). Items marked **observed** come from that run. Nothing was run on a real project, and no assistant, MCP server or index took part.

1. Commit or back up your project first, including `.claude/settings.json`, `.github/workflows/`, and any file you keep inside a platform tree. The installer spares the client-owned files, but it replaces each platform tree wholesale, so a file of yours in one is deleted (**observed** for `.opencode/agents/`).
2. In the installer clone, check out the `v11.0.0` tag, then run `scripts/install.sh --target <your-project> --platform <name> --update`.
3. What the rollback restores:
   - the `tools:` form of the generated Opencode agents, without the `permission:` maps (**observed**), so **SEC-T840-01 returns**: the generated agents get Opencode's defaults for shell, edit, web and delegation again, and the orchestrators can launch any agent;
   - the Brave 2.1.4 and `server-filesystem` 1.0.0 pins in the generated MCP configs (**observed** in `.mcp.json`), so SEC-T702-09 returns, whose v11.0.0 acceptance does not cover a rollback after v12.0.0 (it covered v11.0.0 only, and its deadline was the first Brave release above 2.1.4), and SEC-T756-07 returns;
   - the v11 files of `implementation/runtime/memory/`, without the `build.py` check of M-6 and the `context-retriever` fixes of M-7 (**observed** in the file list; not called).
4. What it does not change: the v11.0.0 installer copies with `rsync -a` without `--checksum`, so the rollback itself can skip a changed file of equal size whose timestamp falls in the same second (v11.0.0 K-39). In the run above it did not (**observed**); in automation that clones and installs in one job, run v11.0.0's M-6 `touch` step before the rollback's `--update`.
5. To go forward again, check out `v12.0.0` and run `--update`. The target returned to the v12 state (**observed**), and M-1 to M-7 apply again.

**For maintainers.** A published tag is not moved or re-created without the user (`CONTRIBUTING.md` § Moving or deleting a pushed tag (retag)). A critical issue after the release is fixed forward through `CONTRIBUTING.md` § Hotfixes. Neither path was rehearsed for this release.
