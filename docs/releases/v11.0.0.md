# Release v11.0.0

## Summary

v11.0.0 is a MAJOR release of the emage.code harness since v10.0.0. It removes the Pi and Gemini CLI platforms (ADR-013, ADR-014): the installer refuses both with an error and a notice and never deletes a project's `.pi/` or `.gemini/`. Cline and Opencode sessions next to `.claude/` now resolve as their own platform, and the `context-retriever` index build refuses more. Read the Migration Guide before you run `--update`: M-1 to M-3 if you used Pi or Gemini CLI, M-4 if you use `context-retriever` from Cline or Opencode, and M-6 for the Node versions and the MCP server environments.

## Install

Latest release: v11.0.0

Install with the installer from a clone of this repository:

```bash
git clone https://gitlab.com/em-age/emage.code.git
cd emage.code
scripts/install.sh --target <your-project> --platform <name>
```

| Platform | `--platform` value |
|----------|-------------------|
| GitHub Copilot (VS Code) | `github` |
| Opencode | `opencode` |
| Claude Code | `claude-code` |
| Cline | `cline` |
| All platforms | `all` |

Pi support was removed in v11.0.0; see Migration Guide item M-1. Gemini CLI support was removed in v11.0.0; see Migration Guide item M-2. Cursor support was removed in v9.0.0.

Update an existing install: add `--update`. `scripts/install.sh --help` lists every option. If you run v9.x or older, first read the Migration Guide of v10.0.0 (`docs/releases/v10.0.0.md`, in the emage.code repository and at the `v10.0.0` tag), and for v8.x or older that of v9.0.0 as well.

The MCP servers launched through `npx` need Node.js 22 (22.23.5 or later), 24 (24.22.3 or later) or 26 (26.13.1 or later) (M-6).

Set the MCP environment variables named in the generated MCP config, then run
`/new-project "Your idea"` in your assistant.

## Highlights

- **Pi and Gemini CLI are no longer supported platforms (ADR-013, ADR-014; T769 to T782).** Four platforms remain: GitHub Copilot (VS Code), Opencode, Claude Code and Cline. `--platform pi` and `--platform gemini` exit 1 before anything is written, and `--update` leaves an existing `.pi/` or `.gemini/` alone, with a notice when the folder carries the generator's marker. Read M-1 and M-2.
- **`context-retriever` on Cline and Opencode (T790; QA-T760-03, SEC-T791-01).** The generated entry now names each platform's own folder, so an install without `.claude/` answers queries, and Cline and Opencode sessions next to `.claude/` now see the entries meant for their platform (M-4).
- **The index build refuses what it used to accept (T790, T795, T797).** A `--project-id` that is not the lower-case form taken from the git remote is refused, and the refusal messages no longer print a remote's credentials (M-5).
- **A fixed dependency in the two Python MCP servers (T824; SEC-T814-01).** Both runtime lock files move `opentelemetry-api` from 1.45.1 to 1.45.2, which fixes CVE-2026-126360. An existing server environment keeps 1.45.1 until you run the upgrade line in M-6.
- **Accepted risks, with the new record rules (ADR-015, ADR-016).** Three `SECURITY:MEDIUM` findings ship under the user's acceptance for v11.0.0 only: K-16 (SEC-T660-01, SEC-T665-01) and K-28 (SEC-T702-09). Two of them have no fix inside the harness, which the rules now allow only under four conditions (M-9).

## Breaking changes

Counting rule (release manager): this section lists, one entry per change, every change of `docs/artifacts/release-v11-audit-v1.md` § 1 that removes a platform, refuses an input an earlier release accepted, or changes what an existing install's sessions see (B-1 to B-6; 6 entries: A-01 to A-04 for a target, A-05 and A-06 for a fork that authors its own knowledge). The verdict count equals the number of entries listed here. The other changes of that section are under Changelog and in M-8 and M-9, and are not counted.

- **A-01** Pi is no longer a supported platform. `scripts/install.sh --platform pi` exits 1 before writing anything; `--platform all` no longer installs `.pi/`. The `pi` manifest, the generated `.pi/` tree (agents, prompts, instructions, skills, `mcp.json`), the `pi` MCP format and tool-name style, the `skipFormats` key of `servers.yaml` and `merge-mcp-json.py --drop-env-form` are removed (ADR-013; B-1, M-1).
- **A-02** Gemini CLI is no longer a supported platform. `scripts/install.sh --platform gemini` exits 1 before writing anything; `--platform all` no longer installs `.gemini/`. The `gemini` manifest, the generated `.gemini/` tree (agents, commands, instructions, skills, the harness entries of `settings.json`, including the post-edit `AfterTool` hook), the `gemini` MCP format, the manifest option `tools: drop`, and the `excludeTools` union and `hooks` note of `merge-mcp-json.py` are removed (ADR-014; B-2, M-2, M-3).
- **A-03** `context-retriever`: the generated entry passes `--platform-root .cline` on Cline and `--platform-root .opencode` on Opencode, not `.claude` everywhere. Next to `.claude/`, Cline and Opencode sessions now resolve as `cline` and `opencode`, so shared-scope entries that name only `claude-code` are no longer returned to them (T790; QA-T760-03, SEC-T791-01; B-4, M-4).
- **A-04** `context-retriever` index build: `build.py` exits 2 on a `--project-id` that is not the derived lower-case `org/repo`, and a remote whose org or repo is `.` or `..` yields no project id (T790, T795; QA-T760-02, SEC-T791-03; B-6, M-5).
- **A-05** (fork authors) A platform manifest with `mcp.format` or `mcpToolNames` set to `pi`, `mcp.format` set to `gemini` or `tools` set to `drop` fails; a pack whose `supportedPlatforms` lists `pi` or `gemini` is rejected by the schema; a leftover `skipFormats` key stops `sync.mjs`; `merge-mcp-json.py --drop-env-form` is gone (ADR-013, ADR-014; B-3, M-7).
- **A-06** (fork authors) An unknown `{{...}}` placeholder in a server's `args` stops `sync.mjs`; only a whole `{{platformDir}}` is known, and an `outputDir` that is not one plain dot-folder name stops the run (T790; B-5, M-7).

## Migration Guide

**Migration from v10.0.0 to v11.0.0.** Do this in order:

1. **Before the update:** commit or back up your project, including any file you keep inside a platform tree: `--update` replaces `.github/`, `.opencode/`, `.claude/`, `.cline/` and `.clinerules/` wholesale. If any automation runs `--platform pi`, `--platform gemini`, or reads `.pi/` or `.gemini/` after `--platform all`, change it first (M-1, M-2).
2. Run the update:

   ```bash
   cd <emage.code clone>
   git fetch --tags && git checkout v11.0.0
   scripts/install.sh --target <your-project> --platform <name> --update
   ```

3. **After the update:** M-1 and M-2 if the installer printed a Pi or Gemini CLI notice; M-3 for Gemini entries you added yourself; M-4 if you use `context-retriever` from Cline or Opencode; M-5 if you script the index build; M-6 for Node and the MCP server environments.

M-7 is for a fork that authors its own knowledge. M-8 is for someone working on releases from an emage.code checkout. M-9 needs no action. On a throwaway target installed by the v10.0.0 installer with `--platform all`, this release's `--update` exited 0, modified about 35 files and added or deleted none, and changed nothing under `.pi/` or `.gemini/`, including a file of the user's own placed in each (observed by the release manager and by QA on 2026-11-13; no assistant, MCP server or index took part). The count depends on timestamps: it was 35 where the target's files were older than the clone's, and 33 (or 30) where they fell in the same second, because the copy then skips files of equal size (K-39, M-6).

**What a target does not receive.** On that throwaway target the install wrote no `scripts/`, `docs/releases/`, `.gitlab-ci.yml`, `CONTRIBUTING.md` or `implementation/PREREQUISITES.md` (observed). Any `scripts/` command in this document runs from an emage.code clone, and any `docs/releases/` path and `implementation/PREREQUISITES.md` are in the emage.code repository.

**Cursor: nothing changes in this release.** No line of `scripts/install.sh` that names Cursor points to this document, so this document carries no Cursor item. The installer's Cursor notices keep pointing to the older documents: `scripts/install.sh:187` and `:1305` name the Cursor migration item in `docs/releases/v9.0.0.md`, and `:1301` holds the advice on `.cursor/mcp.json`, which names M-9 in `docs/releases/v8.0.0.md`. The lines that point here are `:192` and `:1327` (Pi) and `:196` and `:1351` (Gemini CLI).

### M-1. Pi is no longer supported (ADR-013; SEC-T773-02)

- `--platform pi`, in any letter case, exits 1 before any write, in a plain install, `--update`, `--projections-only` and `--dry-run`, with: "error: platform 'pi' was removed in v11.0.0 (see docs/releases/v11.0.0.md). Existing .pi/ files in your project are not touched. Nothing was written." (`scripts/install.sh:191-194`; exit 1 observed on a throwaway target).
- `--update` and `--projections-only` no longer touch `.pi/` (before, they replaced it and deleted files you had added there). While the installer finds a harness-generated `.pi/`, it prints a note (`scripts/install.sh:1313-1327`, called from `validate_before_update` at `:1358`; observed). **A `.pi/` without a generator marker gets no notice:** the notice needs `.pi/.generated-manifest.json` naming `"platform": "pi"` or `.pi/mcp.json.provenance.json`, and a symlinked `.pi` or marker is not read (SEC-T773-02).
- **To clean up, in this order:**
  1. In `.pi/mcp.json`, remove the servers listed under `generatorOwnedKeys` in `.pi/mcp.json.provenance.json`, and keep your own. Do this first: the manifest's `files` list also names the sidecar.
  2. Delete the paths listed under `files` in `.pi/.generated-manifest.json` except `mcp.json`; the sidecar goes with them. A path that is already missing, such as `prompts/prepare-release.md`, which a target never received, is fine.
  3. Delete the manifest and the empty folders.

  Do not delete `.pi/` as a whole unless you know nothing else, Pi itself included, keeps files there. QA ran this order on a copy of a v10.0.0 install and was left with only its own server in `mcp.json` and its own file (QA-T818-02).
- **If you keep it, it is frozen.** MCP server pins, the Playwright hardening and the GitLab tool grants in `.pi/agents/*.md` receive no updates, and nothing prunes them.
- Automation that runs `--platform pi` now fails with exit 1; automation that runs `--platform all` and reads `.pi/` must change.
- Rollback: the v10.x installer with `--update` recreates `.pi/` and, as before, replaces it wholesale, deleting files you added there (observed; see the Rollback Plan).

### M-2. Gemini CLI is no longer supported (ADR-014; SEC-T780-05)

- `--platform gemini`, in any letter case, exits 1 before any write, with the matching message (`scripts/install.sh:195-198`; exit 1 observed with `GEMINI`).
- `--update` and `--projections-only` no longer touch `.gemini/` (before, they replaced it and deleted files you had added there, Gemini CLI's own included). While the installer finds a harness-written `.gemini/` (`.gemini/settings.json.provenance.json` or the manifest), it prints a note (`scripts/install.sh:1336-1351`, called at `:1359`; observed). It never reads `.gemini/settings.json` or `.gemini/.env`, and never deletes anything there. A `.gemini/` without a marker gets no notice.
- **Do not delete `.gemini/settings.json` or the `.gemini/` folder**: Gemini CLI keeps your own settings, `.env` and other files there. **To clean up, in this order:**
  1. In `.gemini/settings.json`, remove the servers listed under `generatorOwnedKeys` in `.gemini/settings.json.provenance.json` (keep any you want as your own) and the harness's post-edit hook under `hooks.AfterTool`; keep every other key. Do this first: the manifest's `files` list also names the sidecar.
  2. Delete the paths listed under `files` in `.gemini/.generated-manifest.json` except `settings.json`; the sidecar goes with them. A path that is already missing is fine.
  3. Delete the manifest and the empty folders.

  QA ran this order on a copy of a v10.0.0 install and was left with `settings.json` holding no harness entry, `.env` and its own file (QA-T818-02).
- **If you keep the harness entries, they are frozen.** MCP server pins, the Playwright hardening and the GitLab entry receive no updates, and Gemini CLI agents and your main session can call every tool of every configured server except the six denied Playwright tools.
- Automation that runs `--platform gemini` now fails with exit 1; automation that runs `--platform all` and reads `.gemini/` must change.
- Rollback: the v10.x installer with `--update` recreates the harness files and, as before, sweeps `.gemini/` and deletes your own files there (observed; see the Rollback Plan).

### M-3. Gemini entries you added yourself outside `.gemini/` (A-22; ADR-014 Q4)

The installer never edits your own client settings. If you added Gemini CLI entries to them yourself, such as an auto-approve entry in `.vscode/settings.json` or `.claude/settings.json`, remove them by hand. For this repository's own user this is user action A-22, and whether it is done is **(unverified)**: nobody opened those files for this document.

### M-4. Cline and Opencode: `context-retriever` platform identity next to `.claude/` (SEC-T791-01; QA-T760-03). After `--update`

- The generated `context-retriever` entry passes `--platform-root .cline` in `.cline/mcp.json` and `--platform-root .opencode` in `.opencode/opencode.json`, where v10 passed `.claude` (observed in the `--update` diff of the throwaway target; `implementation/knowledge/mcp/servers.yaml:184-196`, `implementation/scripts/sync.mjs:224-250`).
- **What your sessions see changes.** Next to `.claude/`, Cline and Opencode sessions now resolve as `cline` and `opencode`. Shared-scope entries that name only `claude-code` are no longer returned to them, and entries naming their platform now are. **Action:** a shared entry meant for every client lists each platform, or uses `["*"]`.
- A Cline or Opencode install without `.claude/` now answers `retrieve`; under v10 it failed at the first query (K-35, closed).
- That a live Cline or Opencode client resolves this way is from source reading and test installs, not a live client **(unverified live)** (K-20).

### M-5. `context-retriever` index build (T790, T795, T797; QA-T760-01, QA-T760-02, QA-T792-1, SEC-T791-02, SEC-T791-03, SEC-T796-01)

- **Fixed, so v10.0.0's two caveats on its M-2 no longer apply.** The install note now prints the line that installs `implementation/runtime/memory/requirements.txt` (`scripts/install.sh:1735`; QA-T760-01), and the build line activates the same `.venv-mcp` first (`:1739-1741`; QA-T792-1):

  ```bash
  python3 -m venv .venv-mcp && source .venv-mcp/bin/activate && pip install -r implementation/runtime/memory/requirements.txt
  source .venv-mcp/bin/activate && python3 -m implementation.runtime.memory.build \
      --project-id <org>/<repo> --own-repo-root . --general-repo-root . \
      --output-dir implementation/runtime/memory/_index/<org>-<repo>
  ```

- **Action, if you script the build:** `build.py` refuses, with exit 2, a `--project-id` that is not in lower-case `org/repo` form (`implementation/runtime/memory/build.py:51-61`; QA-T760-02). A script that passes another letter case must change. **It does not compare the id with the git remote `origin`**, so pass the remote's own id in lower case: a lower-case id that is not the remote's, such as `acme/other` for the remote `Acme/Widget`, is accepted and the index is written (exit 0), and the server, which takes its id from the remote, then filters every project entry out and `retrieve` returns an empty result with no error (run by QA, QA-T818-03, graded `SECURITY:LOW` in the T820 addendum § 2; the equality check and a corrected note are tracked for a later release). The note the installer prints says "--project-id must be that same lower-case org/repo; the build refuses any other" (`scripts/install.sh:1746`), which overstates the check in the same way; the code is unchanged in this release. Use lower case in your entries' `project_id` as well: the value that gave v10's silent empty result was the entry's `project_id`, not `--project-id` (TL-T763-01).
- The build names on stderr, by path only, every own-repo project-scope entry whose `project_id` is not `--project-id` (SEC-T791-02).
- A remote whose org or repo is `.` or `..` yields no project id, so the server does not start (the default) or every `retrieve` fails (with `--index-dir`) (SEC-T791-03). Whether any real host allows such a path is **(unverified)**.
- Refusal messages redact a remote's userinfo (SEC-T796-01).
- K-35, the failing `retrieve` on an install without `.claude/`, is closed by M-4 (TL-T763-02).

### M-6. Node for the `npx` MCP servers, and existing MCP server environments (SEC-T784-01, SEC-T825-02, SEC-T814-01, SEC-T825-01)

- **Node minimums, per release line:** Node.js 22 (22.23.5 or later), 24 (24.22.3 or later) or 26 (26.13.1 or later), the November 2026 Node security releases. The odd-numbered and end-of-life lines 18, 20, 23 and 25 are not supported, so "Node.js 18+" no longer holds (`implementation/PREREQUISITES.md:4`; the check at `:227` is `node --version` with "v22 ≥ 22.23.5, v24 ≥ 24.22.3, or v26 ≥ 26.13.1"). Nothing in the installer or the servers checks your Node version **(unverified)**: check it yourself.
- **Existing MCP server environments.** This release fixes SEC-T814-01: `opentelemetry-api` 1.45.1, CVE-2026-126360 (GHSA-mf5v-w3w3-f6cg, a ReDoS in `traceparent` parsing), is replaced by 1.45.2 in `implementation/runtime/security/requirements-mcp-server.lock.txt` and `implementation/runtime/memory/requirements-mcp-server.lock.txt` (T824; graded `SECURITY:LOW` by T825). A virtual environment you built before keeps 1.45.1, because `pip install -r` does not upgrade a dependency that is already satisfied, and the unhashed `requirements-mcp-server.txt` carries no floor (SEC-T825-01, tracked). **Action:** in the environment that runs each server, from your project root, run:

  ```bash
  pip install --require-hashes -r implementation/runtime/security/requirements-mcp-server.lock.txt
  pip install --require-hashes -r implementation/runtime/memory/requirements-mcp-server.lock.txt
  ```

  The lines were not run for this document **(unverified)**; the lock files and their 1.45.2 pin at line 244 were read on the release branch.

- **Check the lock files after `--update` (QA-T818-01, TD-T774-01).** The installer's copy can skip a changed file of equal size whose timestamp falls in the same second as the target's, and the two lock files change only `1.45.1` to `1.45.2`, at the same size. QA reproduced this on a target checked out in the same second as the clone: both locks kept 1.45.1, and the lines above would then reinstall 1.45.1 without a warning. Before you run them, from your project root:

  ```bash
  grep '^opentelemetry-api' implementation/runtime/*/requirements-mcp-server.lock.txt
  ```

  Both lines must show `opentelemetry-api==1.45.2`. If one shows 1.45.1, refresh the timestamps in the emage.code clone and run `--update` again, then repeat the check:

  ```bash
  cd <emage.code clone>
  find implementation -type f -exec touch {} +
  scripts/install.sh --target <your-project> --platform <name> --update
  ```

  This workaround is QA's (QA-T818-01) and was not run for this document **(unverified)**. The `grep` detects only the lock files, and other files can be skipped too (K-39). **Automation that clones emage.code and installs in the same job should run the `touch` step before every `--update`**, whatever the `grep` shows. The code fix is tracked for a later release (K-39).

### M-8. Release authors and maintainers of this repository. Not for a target

The rules of v10.0.0's M-7 still hold: `scripts/verify-release-docs.py` has no change since v10.0.0. In addition:

A tag pipeline without a runner carrying that tag leaves the three tag jobs pending. A digest change of the tag jobs' image needs the runner's `allowed_images` changed with it (`docs/wiki/mcp-pin-bump-checklist.md` § 3; plan-159).
- **CA-chain control.** `ca-chain-check-python` and `ca-chain-check-node` (`.gitlab-ci.yml:160`, `:181`; `scripts/check-ca-chains.sh`) must pass on the release commit, in its branch or merge request pipeline. Neither runs on a tag.
- **`unit-tests`** now installs `openssl~=3.5` (`.gitlab-ci.yml:104`) and fetches the `v10.0.0` tag (`:116`) for the removed-platform test.
- **A user-accepted `SECURITY:MEDIUM` with no harness fix** needs the four ADR-016 conditions in its Conditions line (M-9).
- **Local gate run.** The gate needs `markdown-it-py` from `ci/requirements-release.txt`, in a virtual environment: `python3 -m pip install --require-hashes --only-binary=:all: -r ci/requirements-release.txt`.

### M-9. Behaviour changes to brief your team on. No action

- **Release gate records (ADR-015, ADR-016; T801 to T806).** The `validation-gates` skill, § Verdict Rules, and the `release-manager` agent's Conditions slots change what a target's own release gate demands of a user-accepted `SECURITY:MEDIUM` (`implementation/knowledge/skills/validation-gates/SKILL.md:70`, `:120`; `implementation/knowledge/agents/release-manager.md:183`). A plan whose fix is "none possible in the harness" is valid only with four conditions: who could close the finding outside the harness, the plain statement that no harness fix exists, a review date as the plan's deadline, and the Security Engineer's review confirming it before the user is asked. A new acceptance cures a passed deadline, and the release document then states that the old deadline passed, its date and the release the old acceptance was given for. Both questions, open at v10.0.0 (SEC-T762-04), are ruled.
- **Text.** Pi and Gemini CLI wording is removed from the shipped knowledge text (`commands/consolidate-memory.md`, `discover-skills.md`, `skillify.md`, the `memory-management` and `skillify` skills, `agents/context-retriever.md`, `implementation/SECURITY.md`). Text only.

## Changelog

Grouping follows `/prepare-release` step 2: documentation, decisions, reviews and tests are listed under Internal, and breaking changes under Breaking changes. The counts in the verdict block are the number of bullets under Features and Fixes. Changes and evidence: `docs/artifacts/release-v11-audit-v1.md` § 1 (`v10.0.0..9acf84dc`, 27 commits that are not merges), with wave 1 of plan-161 after it. `CHANGELOG.md` did not change in this range; its entry is the release job's.

### Features

- **F-01** Read-only notices for a `.pi/` or `.gemini/` that an earlier release generated, and the removed-platform errors that name this document (T771, T778; ADR-013 D5, ADR-014 D4; per `security-review-t773-pi-removal-v1.md`, `security-review-t780-gemini-removal-v1.md`).

- **F-03** (maintainers) CA-chain control for the pinned CI images, two jobs and `scripts/check-ca-chains.sh` (T766, T767; SEC-T756-02; per `security-review-t768-ca-control-v1.md`).

## Rollback Plan

**Tested for the installed files, on a throwaway target; not tested with a live client.** On 2026-11-13 the release manager installed the `v10.0.0` tree, from a `git archive` of that tag, with `--platform all` into an empty git repository, and added a file of the user's own inside `.pi/` and inside `.gemini/`. This tree's `--update` then exited 0. The `v10.0.0` installer's `--platform all --update` exited 0 and brought the target back to its v10 state, except that it deleted both of the user's own files. This tree's `--update` again exited 0, and the target was identical to the first v11 state (`git diff`). Items marked **observed** come from that run. Nothing was run on a real project, and no assistant, MCP server or index took part.

1. Commit or back up your project first, including `.claude/settings.json`, `.github/workflows/`, and any file you keep inside a platform tree, `.pi/` and `.gemini/` included. The installer spares the client-owned files, but it replaces each platform tree wholesale, so a file of yours in one is deleted.
2. In the installer clone, check out the `v10.0.0` tag, then run `scripts/install.sh --target <your-project> --platform <name> --update`.
3. What the rollback restores:
   - `.pi/` and `.gemini/`, recreated by the v10 installer, which, as before, deletes files you added there (**observed**).
   - `--platform-root .claude` in the `context-retriever` entries of `.cline/mcp.json` and `.opencode/opencode.json` (**observed**), and with it v10's platform identity and the failing `retrieve` without `.claude/` (K-35; inferred, not run).
   - The v10 files of `implementation/runtime/`, including the lock files with `opentelemetry-api` 1.45.1, so **SEC-T814-01 returns** (**observed** in the lock files) and the index-build refusals of M-5 are lost (inferred from the code; not called).
   - The v10 knowledge text, without the ADR-015 and ADR-016 rules (inferred from the file list; not read file by file).
4. What it does not change: an MCP server environment you upgraded with M-6's lines keeps 1.45.2 until you reinstall it from the v10 lock (inferred, not run).
5. To go forward again, check out `v11.0.0` and run `--update`. The target returned to the v11 state (**observed**), and M-1 to M-6 apply again.
