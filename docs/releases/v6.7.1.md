## Internal

- T348: synced `main` with `develop` for v6.7.0 (`release/v6.7.0 → main`, MR !125). Confirmed a
  phantom-conflict false alarm (`main` had zero independent commits since T339) before resolving by
  taking `develop`'s side on 32 files, verified byte-identical. `squash=false` was requested but the
  GitLab API reported `squash=true` anyway (the same pattern previously seen on MR !103/!109);
  T341's `scripts/verify-main-sync-merge.py` caught it immediately — its first real production use —
  instead of surfacing a release cycle later. Recovered via `chore/restore-ancestry-v6.7.0` (MR
  !126), since `CONTRIBUTING.md`'s then-documented recovery procedure (direct push to `main`) does
  not work as written (`main` has `push_access_levels: ['No one']`, same as `develop`). Along the
  way, found that PUT-updating the MR resource's own `squash` attribute to `false` *before* calling
  `/merge` (not just passing `squash: false` in the merge call body) reliably prevented the squash on
  MR !126 — flagged as a follow-up candidate and actioned in T349 below. Both `main` pipelines
  verified green; `main` and `develop` confirmed content-identical. No develop-side code artifact.
- T349: fixed `CONTRIBUTING.md`'s release/`main`-sync merge procedure per T348's discovery.
  "Cutting a release" step 6 now documents the PUT-first squash sequence (PUT `squash=false` on the
  MR resource before calling `/merge`) as the standard `release/* → main` merge step, with an honest
  confidence caveat (1 confirmed success vs. 3 prior failures of the old `squash:false`-in-merge-body
  approach). "Recovery procedure" no longer tells the operator to `git push` directly to `main`
  (confirmed impossible — `push_access_levels: ['No one']`) — replaced with the actual branch+MR
  sequence T348 used successfully. `scripts/verify-main-sync-merge.py` left unchanged (still the
  safety net). Process-doc fix only, no shippable code capability.
- Task ledger: T348–T349 archived to `docs/tasks/completed-tasks.md`.
